JavaScript · Bài 13

null và undefined — hai kiểu rỗng khác nhau

undefined là máy nói "chưa có ai gán vào đây". null là người viết nói "chỗ này cố ý để trống". Hai câu khác nhau, và JavaScript đối xử với chúng khác nhau ở đúng những chỗ bạn không ngờ nhất — tham số mặc định, JSON, và phép so sánh.

Là gì

Ô chưa ai điền, và ô bị gạch chéo

Hãy nghĩ tới một tờ khai giấy. Ô "Số điện thoại phụ" bỏ trắng — không ai biết là người khai quên, hay không có, hay chưa tới lượt điền. Đó là undefined. Còn ô bị người khai gạch chéo — rõ ràng có người đã đọc ô đó và quyết định "không có gì ở đây". Đó là null.

Khác biệt không nằm ở giá trị, mà nằm ở ai tạo ra nó. undefined do máy sinh ra, tự động, ở những chỗ không ai gán gì cả. null thì không bao giờ tự xuất hiện — nó chỉ có mặt khi một người gõ nó ra, hoặc khi máy chủ gửi nó về.

let a;                       // máy tự điền
console.log(a);              // undefined

let b = null;                // người viết chủ động khai
console.log(b);              // null

// Đây là chỗ khác biệt trở thành thông tin có ích khi tìm lỗi:
// gặp undefined ngoài ý muốn → thường là LỖI của bạn (quên gán, sai tên thuộc tính).
// gặp null ngoài ý muốn     → thường là DỮ LIỆU (máy chủ trả về đúng như vậy).

Câu chốt cả bài: undefined là "chưa có", null là "cố ý không có". Trong 90% mã nguồn bạn không cần phân biệt — ?? và ?. gom cả hai lại. Rắc rối chỉ nổ ra ở đúng 10% còn lại: tham số mặc định, JSON, và toán tử so sánh.

Cơ chế

Một bên có năm cửa tự sinh, một bên chỉ có hai

Nhớ danh sách bên trái là đủ để không bao giờ phải đoán. Và nhớ một điều nữa: biến chưa khai báo hoàn toàn không phải undefined — truy cập nó ném ReferenceError (lỗi tham chiếu — trình chạy không tìm thấy cái tên đó). Đây là chỗ rất nhiều người nói sai.

let daKhaiBao;
console.log(daKhaiBao);       // undefined — hợp lệ

console.log(chuaKhaiBao);     // ✗ ReferenceError: chuaKhaiBao is not defined

// Chỉ typeof là không ném — đó là ngoại lệ duy nhất của ngôn ngữ.
console.log(typeof chuaKhaiBao);   // 'undefined'

Mười chỗ hai đứa cư xử khác nhau

Bảng này là toàn bộ phần cần thuộc. Mọi lỗi liên quan tới rỗng trong JavaScript đều nằm ở một trong các dòng dưới đây.

Bẫy nổi tiếng nhất

null vừa không bằng 0, vừa lớn hơn hoặc bằng 0

Hai toán tử này chạy hai luật ép kiểu khác nhau. == có luật riêng cho rỗng; >= thì ép thẳng sang số, mà Number(null) là 0.

null == 0;    // false
null > 0;     // false
null >= 0;    // true  ← không ai đoán được
Hay cắn ở dự án thật

Tham số mặc định không ăn null

Máy chủ trả null cho trường trống, bạn tưởng mặc định sẽ đỡ. Không hề — mặc định chỉ kích hoạt với undefined.

function chao(ten = 'khách') {
  return 'Chào ' + ten;
}
chao();               // 'Chào khách'
chao(undefined);      // 'Chào khách'
chao(null);           // 'Chào null'  ✗

// Cách chữa: đưa về undefined trước, hoặc dùng ??
chao(tuMayChu ?? undefined);
Mất dữ liệu âm thầm

JSON không biết undefined là gì

Chuẩn JSON chỉ có null. Gửi đi rồi nhận về là đối tượng đã đổi hình dạng — và không có lỗi nào được ném ra.

JSON.stringify({ a: undefined, b: null });
// '{"b":null}'   ← mất hẳn khoá a

JSON.stringify([undefined, null]);
// '[null,null]'  ← đổi thành null

JSON.stringify(undefined);
// undefined      ← không phải chuỗi!

Được gì — mất gì

Ưu điểm và nhược điểm của việc có hai kiểu rỗng

+Mặt lợi

  • Biết ngay lỗi đến từ đâu. undefined bất ngờ là lỗi mã nguồn; null bất ngờ là dữ liệu máy chủ. Tiết kiệm nửa thời gian tìm lỗi.
  • Phân biệt "chưa gửi" với "gửi giá trị trống". Trong một lời gọi cập nhật một phần, bỏ khoá đi và gửi null là hai ý định khác nhau — và JSON.stringify diễn đạt đúng cả hai.
  • null là cách nói "đừng dùng mặc định". Truyền null vào tham số có giá trị mặc định là cố tình từ chối nó.
  • ?? và ?. gom cả hai. Phần lớn mã nguồn không cần quan tâm khác biệt — chỉ cần một toán tử.
  • TypeScript bắt được cả hai lúc biên dịch. Bật strictNullChecks là mọi chỗ rỗng đều phải xử lý trước khi chạy.

Hai ý định, hai cách gửi

// "Đừng đụng tới ghi chú" — khoá biến mất khỏi JSON
{ ten: 'An', ghiChu: undefined }
// gửi đi: {"ten":"An"}

// "Xoá ghi chú đi" — gửi null rõ ràng
{ ten: 'An', ghiChu: null }
// gửi đi: {"ten":"An","ghiChu":null}

−Mặt hại

  • typeof null trả về 'object'. Một lỗi từ bản JavaScript đầu tiên, sửa thì vỡ nửa web nên vĩnh viễn nằm đó. Kiểm tra kiểu bằng typeof là sai ngay từ dòng đầu.
  • Hai cách kiểm tra cho hai kết quả. null == undefined đúng nhưng null === undefined sai — người đọc mã phải tự nhớ bạn đang dùng cái nào.
  • Toán tử so sánh không nhất quán. null == 0 sai mà null >= 0 đúng. Không có cách nào suy luận ra, chỉ có học thuộc.
  • Tham số mặc định bỏ qua null. Lỗi kinh điển khi nối máy chủ: trường trống trả về null, mặc định không chạy, giá trị null chui thẳng vào giao diện.
  • Đi vòng qua JSON là mất dữ liệu. Đối tượng gửi đi và đối tượng nhận về không còn giống nhau, mà không có cảnh báo nào.
  • Hai thế giới quen hai loại khác nhau. Backend hay dùng null, mã JavaScript hay sinh undefined — không chuẩn hoá ở ranh giới là cả hai lẫn lộn khắp nơi.

Ba cái bẫy hay gặp nhất

// ✗ tưởng lọc được null
if (typeof x === 'object') { ... }   // null lọt vào đây

// ✗ tưởng mặc định sẽ đỡ
const { trang = 1 } = { trang: null };
console.log(trang);                  // null, không phải 1

// ✗ tưởng gửi đi rồi nhận về là như cũ
const goc = { a: undefined };
const sau = JSON.parse(JSON.stringify(goc));
console.log('a' in goc, 'a' in sau);  // true false

Cách sống chung an toàn: đặt một quy ước và giữ nó. Trong mã của mình, chỉ sinh undefined — đừng gán null tay. Coi null là thứ chỉ tồn tại ở ranh giới với máy chủ, và chuẩn hoá nó ngay tại tầng gọi dịch vụ bằng ?? undefined. Kiểm tra rỗng thì viết x == null — đây là đúng một chỗ nên dùng ==, vì nó bắt gọn cả hai trong một phép so sánh, và mọi bộ kiểm mã nguồn đều cho phép ngoại lệ này. Đừng bao giờ dùng typeof để bắt null. Và bật strictNullChecks để trình biên dịch làm phần việc ghi nhớ thay bạn.

Nói trong phỏng vấn

Trả lời thế nào cho gọn

Trả lời 30 giây: Cả hai đều là giá trị rỗng, nhưng khác nhau ở nguồn gốc. undefined do máy sinh tự động — biến chưa gán, tham số thiếu, thuộc tính không tồn tại, hàm không return. null thì không bao giờ tự xuất hiện, nó chỉ có khi người viết gán hoặc máy chủ trả về, và mang nghĩa "cố ý để trống". Về hành vi thì null == undefined đúng nhưng === sai; typeof null trả 'object' vì một lỗi cũ của ngôn ngữ; và quan trọng nhất trong thực tế là tham số mặc định chỉ kích hoạt với undefined, không với null.

Hay bị hỏi

Khác nhau giữa null và undefined?

Đừng chỉ nói "một cái là chưa gán, một cái là rỗng". Trả lời ba tầng: ý nghĩa (chưa có vs cố ý không có), ai sinh ra (máy vs người), và hành vi khác nhau ở đâu (mặc định, JSON, ép kiểu). Tầng thứ ba là tầng phân biệt ứng viên.

Câu hỏi bẫy

typeof null trả về gì?

'object'. Lý do: bản JavaScript đầu tiên lưu giá trị kèm một thẻ kiểu, và null có thẻ trùng với đối tượng. Sửa thì vỡ vô số trang web đang chạy nên nó được giữ nguyên vĩnh viễn. Hệ quả thực dụng: muốn bắt null thì viết x === null, đừng dùng typeof.

Câu hỏi bẫy

null == 0 và null >= 0 cho ra gì?

false và true. Vì == có luật riêng cho rỗng — null chỉ lỏng-bằng undefined và chính nó, không ép sang số. Còn toán tử so sánh lớn-bé thì ép thẳng sang số, mà Number(null) là 0. Hai toán tử, hai luật.

Câu hỏi loại ứng viên

Trong dự án của bạn, hai cái này được xử lý thế nào?

Đây là câu hỏi về kinh nghiệm, không phải về ngôn ngữ. Trả lời bằng một quy ước cụ thể: mã nội bộ chỉ sinh undefined, null chỉ được chấp nhận ở tầng gọi máy chủ và bị chuẩn hoá ngay tại đó, kiểm tra rỗng thống nhất bằng x == null, và bật strictNullChecks. Kể kèm một lỗi thật đã gặp thì càng tốt.

Trả lời sai kinh điển: "undefined là biến chưa được khai báo." Sai. Biến chưa khai báo mà đem ra dùng thì ném ReferenceError chứ không cho ra undefined. undefined là biến đã khai báo nhưng chưa gán giá trị. Ngoại lệ duy nhất là typeof — nó không ném lỗi với tên chưa tồn tại, và chính ngoại lệ đó khiến nhiều người nhớ nhầm suốt nhiều năm.
