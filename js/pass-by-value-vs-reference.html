Pass by value và pass by reference

Truyền một biến vào hàm rồi sửa — lúc thì bên ngoài đổi theo, lúc thì không. Sự thật là JavaScript chỉ có MỘT cách truyền, nhưng cái được truyền lại có hai loại.

Là gì

Hai khái niệm, và cái tên thứ ba mới đúng

Pass by value (truyền tham trị) là đưa cho hàm một bản sao. Hàm sửa bản sao, bản gốc không hề hấn.

Pass by reference (truyền tham chiếu) là đưa cho hàm chính cái biến của bạn. Hàm gán lại tham số thì biến gốc bên ngoài cũng đổi theo. C++ và C# (với từ khoá ref) làm được điều này.

JavaScript luôn luôn là pass by value — không có ngoại lệ. Chỉ có điều: với object, cái “value” được chép sang chính là địa chỉ của object. Vì thế người ta gọi riêng trường hợp này là pass by sharing (truyền theo chia sẻ): hai bên chia sẻ cùng một object, nhưng mỗi bên giữ một tấm chìa khoá riêng.

Cơ chế

Phép thử phân biệt: SỬA RUỘT hay GÁN LẠI

Chỉ cần nhớ một câu: sửa ruột thì bên ngoài thấy, gán lại thì không.

function suaRuot(o)  { o.ten = 'Bình'; }
function ganLai(o)   { o = { ten: 'Bình' }; }
function tangSo(n)   { n++; }

const nguoi = { ten: 'An' };
let tuoi = 20;

suaRuot(nguoi);  console.log(nguoi.ten);  // 'Bình' ← thấy
ganLai(nguoi);   console.log(nguoi.ten);  // 'Bình' ← KHÔNG đổi tiếp
tangSo(tuoi);    console.log(tuoi);       // 20     ← không đổi

Chính vì ganLai không có tác dụng ra ngoài, ta khẳng định được JavaScript không hề pass by reference. Nếu là tham chiếu thật, dòng thứ hai đã đổi được biến nguoi.

Được gì — mất gì

Ưu điểm và nhược điểm

+Mặt lợi

  • Truyền object rất rẻ. Một mảng khổng lồ đi qua chục lớp hàm cũng chỉ tốn bằng vài con trỏ.
  • Chia sẻ state dễ dàng. Service, store, cache đều dựa vào việc nhiều nơi cùng nhìn một object.
  • Số và chuỗi luôn an toàn. Không bao giờ phải lo hàm khác sửa trộm một biến nguyên thuỷ của bạn.
  • Luật đơn giản. Chỉ một cơ chế duy nhất cho mọi kiểu — khác hẳn ngôn ngữ có cả ref/out/const&.

Ví dụ mặt lợi

function capNhatKho(kho) { kho.tonKho -= 1; }   // sửa ruột → mọi nơi thấy
function demLai(n) { n = 0; }                   // số thì an toàn tuyệt đối

const kho = { tonKho: 10 };
let soLan = 5;
capNhatKho(kho); demLai(soLan);
console.log(kho.tonKho, soLan);                 // 9 5

−Mặt hại

  • Tác dụng phụ ngầm. Truyền một object vào hàm của thư viện lạ, không có gì đảm bảo nó không sửa dữ liệu của bạn.
  • Bug dùng chung hằng số. Một object cấu hình khai ở tầng module, bị một màn hình sửa, mọi màn hình khác lãnh đủ.
  • Không "trả về qua tham số" được. Muốn hàm trả nhiều giá trị thì phải return object/mảng, không thể gán lại tham số.
  • Dễ giải thích sai. Rất nhiều tài liệu (và phỏng vấn) nói JS "pass by reference với object" — cách nói đó khiến bạn dự đoán sai đúng ở tình huống gán lại.

Ví dụ mặt hại

function sapXep(ds) { return ds.sort(); }   // ✗ sort sửa TẠI CHỖ

const goc = [3, 1, 2];
const daSap = sapXep(goc);
console.log(goc);            // [1, 2, 3] — mảng gốc đã bị đổi
// chữa: return [...ds].sort();

function thayThe(o) { o = { moi: true }; }   // gán lại → không ra ngoài
const a = {}; thayThe(a);
console.log(a);              // {} — nhiều người tưởng sẽ là { moi: true }

Thói quen nên có: hàm không sửa tham số. Cần thay đổi thì tạo bản mới rồi return — const moi = { ...cu, ten }. Với dữ liệu quan trọng đưa ra ngoài, dùng Object.freeze hoặc structuredClone để chặn từ gốc.
