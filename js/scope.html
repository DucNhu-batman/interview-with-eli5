Scope — phạm vi truy cập

Vì sao có biến chỗ này gọi được, chỗ kia lại "không tồn tại"? Câu trả lời nằm ở các lớp phòng lồng nhau mà JavaScript dựng lên quanh mỗi biến.

Là gì

Những căn phòng lồng nhau

Scope (phạm vi — vùng code mà một biến còn “nhìn thấy được”) giống một dãy phòng lồng trong nhau. Đứng ở phòng con, bạn nhìn ra được đồ đạc của phòng cha và của cả căn nhà. Nhưng đứng ở phòng cha, bạn không nhìn được vào trong phòng con.

JavaScript có bốn loại phòng:

  1. Global scope (phạm vi toàn cục) — cả căn nhà. Biến khai báo ngoài mọi hàm, ai cũng thấy.
  2. Function scope (phạm vi hàm) — mỗi lần gọi hàm là dựng một phòng mới. var chỉ tôn trọng loại phòng này.
  3. Block scope (phạm vi khối) — mọi cặp ngoặc nhọn { }: thân if, thân for, một khối trần. Chỉ let và const tôn trọng.
  4. Module scope (phạm vi mô-đun) — mỗi file ES module là một phòng riêng, không rò biến ra ngoài.

Cơ chế

Scope chain — tra biến từ trong ra ngoài

Khi gặp một cái tên, JavaScript tìm trong phòng hiện tại trước. Không có thì bước ra phòng ngoài, rồi ngoài nữa, tới tận global. Hết đường mà vẫn không thấy thì báo ReferenceError. Chuỗi tìm kiếm đó gọi là scope chain (chuỗi phạm vi), và nó chỉ đi một chiều ra ngoài.

const app = 'BDQS';              // global

function tinhTien() {
  var thue = 0.1;               // function scope
  if (true) {
    let tam = 5;                // block scope
    console.log(app, thue, tam);  // ✓ thấy cả ba
  }
  console.log(tam);               // ✗ ReferenceError: tam is not defined
}

Hai điều hay nhầm

Lexical scope và shadowing

Lexical scope (phạm vi tĩnh) nghĩa là phạm vi được quyết định lúc bạn viết code, chứ không phải lúc gọi. Hàm nhớ nơi nó được sinh ra, không quan tâm ai gọi nó và gọi từ đâu:

const ten = 'ngoài';
function in1() { console.log(ten); }

function chay() {
  const ten = 'trong';
  in1();                          // in ra 'ngoài' — vì in1 được VIẾT ở ngoài
}

Shadowing (che biến) là khai một biến trùng tên ở phòng trong. Biến ngoài không mất, chỉ bị che khuất trong phạm vi đó — rất tiện, nhưng cũng là nguồn nhầm lẫn kinh điển khi đọc code người khác.

Mẹo đọc nhanh: gặp một biến lạ, hãy tìm ngược từ chỗ dùng ra ngoài. Nơi khai báo gần nhất tính từ trong ra chính là biến đang được dùng.

Được gì — mất gì

Ưu điểm và nhược điểm

+Mặt lợi

  • Tránh đụng tên. Hai hàm cùng đặt biến i, data, result mà không giẫm chân nhau.
  • Dọn bộ nhớ tự động. Hàm chạy xong, phòng của nó bị dẹp; bộ thu gom rác (garbage collector) thu hồi.
  • Đóng gói dữ liệu riêng tư. Kết hợp với closure (bao đóng), scope là cách duy nhất tạo biến "private" thật sự trong JavaScript thuần.
  • Code dễ đoán. Nhìn một hàm là biết nó đọc/ghi những gì, không phải quét cả file.

Ví dụ mặt lợi

function taoBoDem() {
  let dem = 0;                    // không ai ngoài hàm này chạm tới được
  return { tang: () => ++dem, xem: () => dem };
}
const b = taoBoDem();
b.tang();
console.log(b.xem(), b.dem);      // 1 undefined — dữ liệu thật sự riêng tư

−Mặt hại

  • Hai luật cùng tồn tại. var theo phạm vi hàm, let/const theo phạm vi khối — trộn lẫn trong một file là mảnh đất của bug.
  • Shadowing gây mù. Sửa nhầm biến bị che, chương trình vẫn chạy nhưng sai âm thầm.
  • Biến toàn cục dễ bị ghi đè. Hai thư viện cùng gán window.config là mất dữ liệu của nhau.
  • Closure giữ scope sống. Một callback còn tham chiếu tới phòng cũ thì cả phòng đó không được thu hồi → rò rỉ bộ nhớ (memory leak).
  • Tra cứu sâu tốn công. Chuỗi scope quá dài khiến engine phải dò nhiều lớp (ảnh hưởng nhỏ, nhưng có thật trong vòng lặp nóng).

Ví dụ mặt hại

function tinhTong(ds) {
  tong = 0;                       // ✗ quên let → tạo biến TOÀN CỤC
  ds.forEach((x) => (tong += x));
  return tong;
}
// Một hàm khác cũng dùng tên "tong" → hai bên ghi đè nhau, không lỗi nào hiện ra

const gia = 100;
function xuLy(gia) { return gia * 2; }   // tham số CHE biến ngoài
xuLy();                                    // NaN — không phải 200

Cạm bẫy hay gặp nhất: quên let/const/var khi gán — tong = 0 trong một hàm sẽ tạo ra biến toàn cục ngoài ý muốn (trừ khi bật strict mode). Cả ứng dụng dùng chung biến đó mà không ai biết.

Thực hành

Bốn nguyên tắc nên theo

  1. Mặc định dùng const; cần gán lại thì let. Chỉ đụng var khi bảo trì code cũ.
  2. Khai báo biến ở phạm vi hẹp nhất có thể — sát chỗ dùng nhất.
  3. Không tạo biến toàn cục. Cần chia sẻ state thì xuất (export) từ một module.
  4. Bật ESLint với no-undef, no-shadow, block-scoped-var để máy soát hộ.
