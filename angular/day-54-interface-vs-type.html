Day 54 — interface hay type: bốn khác biệt thật, còn lại là phong cách

TypeScript cho bạn hai cách đặt tên cho một kiểu. Chúng giống nhau tới chín phần mười. Bốn chỗ khác nhau còn lại mới là thứ quyết định bạn chọn cái nào — và là thứ người phỏng vấn muốn nghe.

Là gì

Một cuốn sổ để ngỏ và một cái nhãn đã niêm phong

TypeScript (ngôn ngữ bổ sung hệ thống kiểu dữ liệu cho JavaScript) có hai từ khoá để đặt tên cho một kiểu. interface là bản mô tả hình dạng của một đối tượng: nó có những trường nào, mỗi trường kiểu gì. type là cái nhãn dán lên một biểu thức kiểu bất kỳ — dán xong là khoá lại.

interface User  { id: number; name: string }
type      UserT = { id: number; name: string }

function chao(u: User) { return 'Chào ' + u.name }

const lan: UserT = { id: 1, name: 'Lan' };
chao(lan);   // ✓ chạy được — TS so hình dạng, không so tên

Đoạn trên chạy được vì TypeScript dùng structural typing (so kiểu theo cấu trúc — hai kiểu cùng hình dạng thì dùng lẫn được, bất kể khai bằng từ khoá nào). Cả hai cũng đều nhận generic (kiểu tổng quát — kiểu nhận tham số như một cái hàm), đều dùng được với extends (mở rộng) và implements (lớp cam kết làm đúng bản mô tả). Ai bảo "type không kế thừa được" là đang nhắc TypeScript của mười năm trước.

Câu chốt cả bài: chỉ có bốn khác biệt thật — gộp khai báo, phạm vi đặt tên, chỗ báo lỗi khi trộn, và tên hiển thị trong thông báo lỗi. Ngoài bốn cái đó ra, chọn cái nào cũng chạy như nhau, vì cả hai đều bị xoá sạch khi biên dịch.

Khác 1

Gộp khai báo: cùng một tên, hai số phận

Đây không phải chuyện học thuật. Nó là cách duy nhất để thêm trường vào một kiểu do thư viện bên ngoài định nghĩa — gọi là module augmentation (bổ sung kiểu cho gói mã có sẵn mà không sửa mã nguồn của nó):

// src/global.d.ts — file chỉ chứa khai báo kiểu, không sinh ra mã chạy
interface Window { dataLayer: unknown[] }   // thêm trường vào Window có sẵn

window.dataLayer.push({ event: 'login' });   // ✓ TS đã biết trường này

Khác 2

Phạm vi đặt tên: nhãn dán được lên mọi thứ

type Status = 'draft' | 'sent' | 'paid'        // union — hoặc cái này hoặc cái kia
type Point  = [number, number]                     // tuple — mảng cố định vị trí và kiểu
type Id     = string                              // primitive — kiểu nguyên thuỷ
type Ev     = `on${Capitalize<'click' | 'blur'>}`  // template literal — ghép chuỗi ở tầng kiểu
type Opt<T>  = { [K in keyof T]?: T[K] }            // mapped type — sinh trường từ kiểu có sẵn
type Un<T>   = T extends Promise<infer U> ? U : T   // conditional type — rẽ nhánh kiểu

interface Status2 = 'draft' | 'sent'
//              ~ không có cú pháp này. interface luôn phải là { … }

Khác 3

Cùng một lỗi, hai chỗ nổ cách nhau năm chục dòng

Trộn hai kiểu có cùng một trường nhưng khác kiểu dữ liệu. interface … extends chặn ngay tại dòng khai báo. Intersection (kiểu giao — dấu &, gộp mọi trường của cả hai) thì không nói gì cả: nó lặng lẽ biến trường đó thành never (kiểu rỗng — không giá trị nào hợp lệ), rồi để lỗi nổ ở một chỗ hoàn toàn khác.

interface — chặn tại nguồn

interface A { id: number }
interface B extends A { id: string }
//        ~ Interface 'B' incorrectly
//          extends interface 'A'.
//          Type 'string' is not
//          assignable to 'number'. ts(2430)

type — trôi xuống hạ nguồn

type A2 = { id: number }
type B2 = A2 & { id: string }  // ✓ không lỗi

declare const b: B2
b.id                        // hover: never
const v: B2 = { id: 1 }
// ✗ 'number' is not assignable to 'never'.

Khác 4

Tên trong thông báo lỗi, và giây build

Khi rê chuột lên một biến, IDE (trình soạn thảo mã có gợi ý và báo lỗi) hiện tooltip (bảng chú thích nhỏ). Với interface, tooltip in đúng cái tên bạn đặt. Với một chuỗi & dài, TypeScript thường bung hết ra — và thông báo lỗi dài theo.

hover trên interface

interface Props extends Base, Audit {
  id: number
}
// hover →  Props
// đọc phát hiểu, lỗi ngắn gọn

hover trên intersection

type PropsT = Base & Audit & {
  id: number
}
// hover →  Base & Audit & { id: number }
// lỗi kéo dài mấy chục dòng

Câu bonus khiến người phỏng vấn gật đầu: tài liệu hiệu năng của chính đội TypeScript khuyên ưu tiên interface hơn intersection khi chỉ cần gộp các hình dạng đối tượng. Lý do: interface tạo ra một kiểu phẳng duy nhất và được cache (nhớ đệm — ghi lại kết quả đã tính để khỏi tính lại) theo tên, còn intersection phải tính lại quan hệ mỗi lần dùng. Trên mã nguồn lớn, khác biệt này đo được bằng giây build (bước dịch toàn bộ dự án ra sản phẩm chạy được).

  1. Là hình dạng đối tượng, và người ngoài cần mở rộng (thư viện, API công khai) → interface.
  2. Là union, tuple, kiểu nguyên thuỷ, hay một phép biến đổi kiểu → type, không có lựa chọn nào khác.
  3. Là hình dạng đối tượng dùng nội bộ → không có đáp án đúng. Cái sai duy nhất là mỗi file chọn một kiểu khác nhau — hãy ghi quy ước vào ESLint (công cụ tự động soát mã theo quy tắc của đội) thay vì tranh luận ở từng lần review.

Được gì — mất gì

Ưu điểm và nhược điểm của interface

+Mặt lợi

  • Mở rộng được từ bên ngoài — cách duy nhất bổ sung kiểu cho Window, Express.Request, hay bất kỳ gói nào bạn không sửa được mã nguồn.
  • Bắt xung đột ngay tại dòng khai báo thay vì để lỗi trôi xuống chỗ dùng.
  • Giữ tên trong tooltip và thông báo lỗi, nên lỗi ngắn và đọc ra nghĩa.
  • Nhanh hơn khi biên dịch — một kiểu phẳng được nhớ đệm theo tên, không phải tính lại mỗi lần dùng.
  • Diễn tả ý định rõ hơn: thấy interface là biết đây là một bản hợp đồng về hình dạng, không phải một phép tính kiểu.

Ví dụ mặt lợi

// Thêm trường vào kiểu của thư viện — chỉ interface làm được
declare global {
  interface Window { dataLayer: unknown[] }
}

−Mặt hại

  • Chỉ mô tả được hình dạng đối tượng — union, tuple, kiểu nguyên thuỷ đều nằm ngoài tầm với.
  • Gộp khai báo là con dao hai lưỡi: người khác có thể âm thầm nhét thêm trường vào interface của bạn ở một file khác mà không có lỗi nào báo.
  • Không làm được phép biến đổi kiểu: Partial, Pick, kiểu điều kiện… đều phải viết bằng type.
  • Trộn nhiều nguồn thì dài dòng hơn so với một dấu &.
  • Không cứu được gì lúc chạy — cũng như type, nó bị xoá sạch sau khi biên dịch.

Ví dụ mặt hại

// Cả ba dòng này interface đều bó tay
type Status  = 'draft' | 'sent';
type Point   = [number, number];
type Ro<T>    = { readonly [K in keyof T]: T[K] };

Cách sống chung an toàn: hình dạng đối tượng công khai — kiểu trả về của API, props của component dùng chung — thì dùng interface. Mọi tổ hợp kiểu còn lại dùng type. Đừng đổi qua đổi lại giữa hai từ khoá cho cùng một khái niệm: cái giá của việc chọn "sai" nhỏ hơn nhiều cái giá của việc mỗi file một kiểu.

Nói trong phỏng vấn

Trả lời thế nào cho gọn

Trả lời 30 giây: Cả hai đều đặt tên cho một kiểu và đều bị xoá sạch khi biên dịch. Khác biệt thật chỉ có bốn: interface gộp được nhiều lần khai báo còn type trùng tên là lỗi; type dán được lên mọi biểu thức kiểu chứ không riêng hình dạng đối tượng; trộn kiểu xung đột thì interface … extends báo lỗi ngay dòng khai báo còn & im lặng biến trường thành never; và interface giữ tên trong thông báo lỗi. Quy ước: hình dạng đối tượng công khai dùng interface, mọi tổ hợp kiểu còn lại dùng type.

Hay bị hỏi

Class implements được cả hai chứ?

Được, miễn kiểu đó có hình dạng đối tượng — nói thêm được vế sau mới ăn điểm: implements một union thì không, vì lớp phải biết chắc mình có những trường nào. Lỗi là A class can only implement an object type… ts(2422).

Câu hỏi bẫy

type có đệ quy được không?

Trả lời “không” là đang nhắc TypeScript của mười năm trước. Được từ bản 3.7: type Json = string | number | Json[] chạy tốt. Cái không được là đệ quy trực tiếp không qua đối tượng hay mảng — type T = T cho ts(2456).

Câu hỏi bẫy

Gộp khai báo là ưu hay nhược?

Trả lời được cả hai mặt mới là câu của người có kinh nghiệm. Ưu: cách duy nhất bổ sung kiểu cho gói bên ngoài. Nhược: trong mã của chính đội mình, ai đó nhét thêm trường vào interface của bạn ở file khác mà không có lỗi nào báo.

Câu hỏi loại ứng viên

Chọn sai thì hỏng gì lúc chạy?

Không hỏng gì cả — và đó chính là điểm phải nói ra. Cả hai bị xoá sạch khi biên dịch, runtime (lúc chương trình chạy trên máy người dùng) không biết chúng tồn tại. Cái giá thật là thông báo lỗi khó đọc, giây build, và những lần tranh luận ở khâu review.

Trả lời sai kinh điển: “Dùng type cho mọi thứ cho nhất quán, interface là di sản.” Sai ở hai chỗ. Bổ sung kiểu cho thư viện bên ngoài — thêm trường vào Window chẳng hạn — type không làm được, chỉ interface mới gộp khai báo được. Và trộn bằng & thì xung đột trường không báo lỗi tại chỗ khai báo mà trôi xuống nơi sử dụng, cách chỗ sai có khi năm chục dòng.
