Vòng đời của một Component

Angular tự gọi giúp bạn tám cái hàm tại tám thời điểm cố định trong đời một khối giao diện. Biết mỗi hàm chạy lúc nào, mấy lần, và tại sao — là xong 80% câu hỏi lifecycle trong phỏng vấn. Mọi ví dụ dưới đây lấy từ chính source code của repo này.

01

Giải thích cho người chưa biết gì

Một component (thành phần giao diện — một mẩu màn hình có HTML riêng, CSS riêng và code riêng, ví dụ cái nút, cái bảng, cái dropdown) không tồn tại mãi mãi. Nó sinh ra khi người dùng mở màn hình đó, sống một lúc, rồi chết khi chuyển sang màn hình khác.

Lifecycle (vòng đời) là chuỗi các mốc đó. Lifecycle hook (móc vòng đời — cái "móc" để bạn treo code của mình vào) là những hàm có tên cố định: nếu bạn khai báo hàm tên đúng như vậy trong class, Angular sẽ tự gọi nó đúng lúc. Bạn không bao giờ gọi tay các hàm này.

Ví von

Coi component như một nhân viên mới. constructor (hàm khởi tạo — hàm chạy khi đối tượng vừa được tạo ra trong bộ nhớ) là lúc ký hợp đồng: mới có tên, chưa có bàn ghế. ngOnInit là buổi onboarding: đã nhận đủ thông tin từ cấp trên, bắt đầu làm việc. ngAfterViewInit là lúc bàn ghế máy tính đã lắp xong — giờ mới sờ được vào đồ đạc. ngOnDestroy là lúc nghỉ việc: phải trả thẻ, tắt máy, huỷ đăng ký — nếu quên thì công ty tốn tiền mãi (đó chính là memory leak — rò rỉ bộ nhớ).

Ba từ nữa cần nói rõ trước khi đi tiếp:

  • Template (khuôn mẫu) — file HTML của component, ví dụ dropdown.component.html.
  • DOM (Document Object Model — cây các thẻ HTML thật mà trình duyệt đang vẽ). Angular tạo template thành DOM.
  • Change Detection — viết tắt CD, "cơ chế phát hiện thay đổi": mỗi khi có sự kiện (click, dữ liệu về từ server, hết timer…), Angular quét lại xem dữ liệu nào đổi để vẽ lại màn hình. Mỗi lần quét như vậy gọi là một nhịp CD. Phần lớn lifecycle hook thực chất là các mốc bên trong một nhịp CD.
02

Thứ tự chạy — bức tranh phải thuộc lòng

Đây là câu hỏi phỏng vấn kinh điển: "Kể thứ tự các lifecycle hook." Sơ đồ dưới là câu trả lời đầy đủ.

Mẹo nhớ

Ba cặp Init → Checked đi liền nhau theo hướng “từ trong ra ngoài”: DoCheck (dữ liệu của chính tôi) → Content (nội dung người ta chiếu vào tôi) → View (template của tôi và các con của tôi). Cứ nhớ data → content → view.

03

Từng hook, và code thật trong repo

constructor()1 lầnchưa phải hook

Không phải lifecycle hook của Angular — nó là của TypeScript/JavaScript. Chạy khi Angular new ra class. Lúc này input (dữ liệu component cha truyền xuống) chưa được gán, DOM chưa tồn tại.

Dùng để
Chỉ dependency injection (DI — tiêm phụ thuộc: Angular tự đưa service vào cho bạn) qua inject(), và đăng ký effect() / afterNextRender() — hai thứ này bắt buộc phải gọi trong "injection context" (ngữ cảnh tiêm phụ thuộc), tức là trong constructor hoặc field initializer.
Không dùng để
Gọi API (giao diện lập trình — ở đây hiểu là gọi HTTP lấy dữ liệu), đọc input, đụng vào DOM.
Bẫy → "Sao không gọi HTTP trong constructor cho gọn?" Vì input chưa có (bạn sẽ gọi với undefined), và constructor chạy cả khi SSR (Server-Side Rendering — kết xuất trang ở phía máy chủ) lẫn khi unit test, làm test khó mock.
Đào sâu: ba lý do tách bạch, và những thứ BẮT BUỘC phải nằm trong constructor

Lý do 1 — Constructor chạy trước khi input được gán

Thứ tự Angular dựng một component:

  1. new MyComponent() — constructor chạy. Input chưa có giá trị.
  2. Angular ghi giá trị input vào instance (thể hiện — đối tượng cụ thể được tạo ra từ class).
  3. ngOnChanges()
  4. ngOnInit() — input đã sẵn sàng.
// @Input() cổ điển
@Input() userId!: string;
constructor(private http: HttpClient) {
  this.http.get(`/api/user/${this.userId}`).subscribe(...);  // → /api/user/undefined
}

Với signal input (input() — kiểu mới repo đang dùng), hậu quả chia hai nhánh, và đây là chỗ hay bị hỏi xoáy:

  • input.required<T>() — đọc trong constructor sẽ ném lỗi lúc chạy: NG0950: Input is required but no value is available yet. Repo có nhiều chỗ khai báo kiểu này: table.component.ts:51, chip-list.component.ts:43.
  • input<T>(giáTrịMặcĐịnh) — không ném lỗi, mà trả về giá trị mặc định. Nguy hiểm hơn: code chạy êm ru nhưng gọi API sai, bug chỉ lộ trên production (môi trường chạy thật).

Lý do 2 — SSR: constructor chạy cả trên máy chủ, nơi không có trình duyệt

Khi bật SSR, Angular chạy chính component đó bằng Node.js để sinh sẵn HTML. Trên máy chủ không tồn tại window, document, localStorage. Constructor chạy ở cả hai nơi, nên code đụng vào trình duyệt đặt trong constructor sẽ làm hỏng lượt kết xuất phía máy chủ.

Repo xử lý bằng cách đẩy việc đó xuống hook muộn hơn rồi chặn cửa — ubck-echarts-core.ts làm đúng ba lần, ở ngOnInit, ngOnDestroy và ngAfterViewInit:

private readonly platformId = inject(PLATFORM_ID);   // inject() thì ĐƯỢC đặt ở đây

ngOnInit() {
  if (!isPlatformBrowser(this.platformId)) { return }   // máy chủ thì thoát luôn
  ...
}

Còn một hệ quả nữa: nếu gọi HTTP trong constructor mà không dùng TransferState (kho dữ liệu máy chủ nhét sẵn vào HTML để phía trình duyệt dùng lại), request sẽ chạy hai lần — một lần trên máy chủ, một lần nữa khi trang được hydrate (trình duyệt "nhận lại" phần HTML có sẵn rồi gắn logic vào). Người dùng thấy màn hình nháy, máy chủ tốn gấp đôi.

Lý do 3 — Unit test không còn chỗ chen vào

Đây là lý do thực dụng nhất. Trong test, TestBed.createComponent() chạy constructor ngay lập tức, còn ngOnInit chỉ chạy khi bạn gọi detectChanges(). Khoảng trống giữa hai mốc đó chính là chỗ bạn cài mock (bản giả lập dùng thay cho thứ thật khi test):

const fixture = TestBed.createComponent(UserCard);   // constructor chạy ở đây
fixture.componentRef.setInput('userId', 42);         // ← chen input vào
httpMock.expectOne('/api/user/42').flush(fakeUser);  // ← chen mock vào
fixture.detectChanges();                             // ngOnInit mới chạy → gọi API

Nếu HTTP nằm trong constructor, request đã bắn xong ngay ở dòng đầu — trước khi bạn kịp gán input, trước khi kịp cấu hình HttpTestingController. Bạn mất khả năng test các nhánh "id khác nhau", và test dễ thành flaky (lúc pass lúc fail tuỳ thứ tự chạy).

Ngoại lệ — thứ bắt buộc phải nằm trong constructor

Đừng trả lời cực đoan kiểu "constructor chỉ được để trống". Có một nhóm API chỉ chạy được trong injection context (ngữ cảnh tiêm phụ thuộc — tức thân constructor, hoặc field initializer: dòng khởi tạo thuộc tính ngay trong class):

inject() · effect() · afterNextRender() · toSignal() · takeUntilDestroyed() (khi không truyền DestroyRef vào).

Repo dùng cả hai vị trí hợp lệ:

// field initializer — vẫn nằm trong injection context
// projects/ui/src/custom/download-progress/component/download-notify/download-notify.component.ts:96
private readonly active = toSignal(this.downloadManager.activeDownload$, { initialValue: [] });

// thân constructor
// projects/ui/src/custom/deferered-section/deferered-section.component.ts:39
constructor() {
  afterNextRender({ read: () => this.handleImplementWhenDomStable() });
  this.destroyRef.onDestroy(() => this.handleComponentDestroy());
}
Ranh giới gọn để nói trong phỏng vấn: constructor để ĐĂNG KÝ, ngOnInit để THỰC THI. Đăng ký thì rẻ và không phụ thuộc input; thực thi thì cần dữ liệu và cần đúng môi trường.

Nếu bị hỏi tiếp: "Angular mới có cách nào gọn hơn ngOnInit không?"

Có. Angular 19 thêm resource()/rxResource(), Angular 20 thêm httpResource(). Chúng khai báo ngay ở field và nhận signal làm tham số, nên tự gọi lại khi input đổi — bỏ được cả ngOnInit lẫn ngOnChanges:

userId = input.required<number>();
user = httpResource(() => `/api/user/${this.userId()}`);   // tự chạy lại khi userId đổi

Repo hiện chưa dùng nhóm API này — nhưng nhắc được nó cho thấy bạn nắm hướng đi của framework, không chỉ thuộc bài cũ.

ngOnChanges(changes: SimpleChanges)mỗi lần input đổi

Chạy trước ngOnInit ở lần đầu, rồi chạy lại mỗi khi component cha gán giá trị mới cho một input. Tham số SimpleChanges là một object dạng { tênInput: { previousValue, currentValue, firstChange } }.

Quan trọng
Angular so sánh theo tham chiếu (reference — địa chỉ của object trong bộ nhớ), không so sánh từng field. Sửa obj.name = 'x' trong mảng cũ thì ngOnChanges không nổ; phải tạo object/mảng mới (immutable — bất biến).
Trong repo
Chỉ 3 chỗ dùng, vì repo đã chuyển sang input() signal + computed().
// projects/ui/src/custom/base/Atoms/cmm-input-switch/cmm-input-switch.component.ts:41
ngOnChanges(changes: SimpleChanges) {
  if (changes['defaultValue']) {
    this._value.set(this.defaultValue());
  }
}
Bẫy → "Dùng input() signal thì ngOnChanges còn chạy không?" — Có. Signal input vẫn được báo cáo trong SimpleChanges. Chứng minh ngay trong repo: ubck-echarts-core.ts khai báo toàn bộ input bằng input() nhưng vẫn cài ngOnChanges để lọc thay đổi.
ngOnInit()1 lần140 chỗ

Chạy đúng một lần, sau lần ngOnChanges đầu tiên. Đây là nơi input đã có giá trị thật → chỗ khởi tạo chuẩn.

Dùng để
Gọi HTTP, subscribe (đăng ký lắng nghe) một Observable (luồng dữ liệu phát ra nhiều lần theo thời gian, của thư viện RxJS), set giá trị mặc định cho form.
Không dùng để
Đo kích thước phần tử hay tìm @ViewChild — DOM chưa chắc có.
// projects/ubck-echarts/src/directives/ubck-echarts-core.ts:144
ngOnInit() {
  if (!isPlatformBrowser(this.platformId)) { return }   // SSR: bỏ qua
  if (!window.ResizeObserver) throw new Error('please install a polyfill');

  this.resizeSub = this.resize$
    .pipe(throttleTime(100, asyncScheduler, { leading: false, trailing: true }))
    .subscribe(() => this.resize());        // ← nhớ huỷ ở ngOnDestroy
}
Bẫy → "ngOnInit chạy mấy lần?" — Một lần cho mỗi instance. Nhưng khi router (bộ định tuyến — thứ đổi màn hình theo URL) dùng lại cùng một component cho URL khác (ví dụ /user/1 → /user/2), Angular không tạo instance mới ⇒ ngOnInit không chạy lại. Phải lắng nghe route.params.
ngDoCheck()mỗi nhịp CD1 chỗ

Chạy ở mọi nhịp change detection — có thể vài trăm lần mỗi giây khi người dùng gõ phím hay rê chuột. Dùng khi bạn cần phát hiện thay đổi mà Angular không thấy được (ví dụ sửa field bên trong object cũ, hoặc trạng thái của FormControl).

// projects/ui/src/custom/validation/core/validation.directive.ts:230
ngDoCheck(): void {
  if (!this.control) return;                // thoát sớm — rẻ nhất có thể
  const currentTouched = this.control.touched;
  let hasChange = false;
  if (this.previousTouched !== currentTouched) {   // tự so sánh thủ công
    this.previousTouched = currentTouched; hasChange = true;
  }
  // ... dirty / valid / disabled ... rồi mới cập nhật giao diện nếu hasChange
}
Bẫy → Đây là hook dễ giết hiệu năng nhất. Quy tắc: thoát sớm, chỉ so sánh giá trị nguyên thuỷ (số, chuỗi, boolean), tuyệt đối không gọi HTTP, không tạo object mới, không console.log. Cả repo chỉ có duy nhất 1 chỗ dùng — đó là con số lành mạnh.

ngAfterViewInit()1 lần35 chỗ

Chạy sau khi template của chính component và toàn bộ component con đã được dựng thành DOM. Đây là thời điểm sớm nhất được phép đo đạc, focus, khởi tạo thư viện bên thứ ba (chart, map, editor…).

// projects/ubck-echarts/src/directives/ubck-echarts-core.ts:200
ngAfterViewInit() {
  if (!isPlatformBrowser(this.platformId)) { return }
  this.initChartTimer = window.setTimeout(() => this.initChart());
}
Bẫy → Vì sao bọc trong setTimeout? Hai lý do: (1) đợi trình duyệt tính xong kích thước thật của thẻ chứa biểu đồ; (2) tránh lỗi ExpressionChangedAfterItHasBeenCheckedError — lỗi kinh điển: bạn đổi dữ liệu sau khi Angular đã kiểm tra xong vòng hiện tại, khiến giá trị hiển thị khác giá trị vừa kiểm. setTimeout đẩy việc sang nhịp sau nên hết lỗi.
ngAfterViewChecked()mỗi nhịp CD

Chạy cuối mỗi nhịp CD, sau khi view đã kiểm tra xong. Đổi state trong đây là cách nhanh nhất để tạo vòng lặp vô tận + lỗi ExpressionChangedAfterItHasBeenChecked.

ngOnDestroy()1 lần45 chỗ

Chạy ngay trước khi Angular gỡ component khỏi DOM. Nhiệm vụ duy nhất: dọn rác. Không dọn ⇒ memory leak: setInterval vẫn chạy, ResizeObserver vẫn theo dõi thẻ đã chết, subscription vẫn giữ tham chiếu tới component đã "chết" nên bộ nhớ không được thu hồi.

// projects/ubck-echarts/src/directives/ubck-echarts-core.ts:181
ngOnDestroy() {
  window.clearTimeout(this.initChartTimer);        // 1. huỷ timer
  if (this.resizeSub) this.resizeSub.unsubscribe(); // 2. huỷ subscription
  if (this.animationFrameID) window.cancelAnimationFrame(this.animationFrameID);
  if (this.resizeOb) this.resizeOb.unobserve(this.el.nativeElement); // 3. ngắt observer
  if (this.loadingSub) this.loadingSub.unsubscribe();
  this.changeFilter.unObserve();
  this.dispose();                                  // 4. trả bộ nhớ cho ECharts
}
Bẫy → "Có phải Observable nào cũng cần unsubscribe?" Không. Những cái tự kết thúc (HttpClient gọi xong là complete, ActivatedRoute được router tự dọn, hoặc dùng pipe async trong template) thì không cần. Cái cần dọn là luồng không bao giờ complete: interval, fromEvent, Subject dùng chung trong service.
04

Content và View khác nhau chỗ nào

Câu hỏi phỏng vấn: "Khác nhau giữa ngAfterContentInit và ngAfterViewInit?". Trả lời ngắn: content là HTML do người khác viết rồi nhét vào tôi; view là HTML do chính tôi viết trong template của mình.

Thứ tự giữa cha và con

Câu hỏi tiếp theo thường là: "Cha và con, ai chạy trước?" Quy tắc: Init đi từ cha xuống con; AfterViewInit đi từ con lên cha — vì cha chỉ "xong view" khi tất cả con đã xong.

05

Vì sao hook lại chạy: Change Detection

Bảy trong tám hook nằm bên trong nhịp change detection. Vậy cái gì kích hoạt nhịp đó?

Mặc định Angular dùng Zone.js — một thư viện "vá" (monkey-patch) các API bất đồng bộ của trình duyệt (setTimeout, sự kiện click, XMLHttpRequest…). Mỗi lần một trong số đó chạy xong, Zone.js báo cho Angular: "có thể có gì đó đổi, quét lại đi". Repo này vẫn đang chạy chế độ Zone.js:

// src/app/app.config.ts:41
provideZoneChangeDetection({ eventCoalescing: true }),
// eventCoalescing: gộp nhiều sự kiện xảy ra sát nhau thành 1 nhịp CD → đỡ tốn

OnPush (ChangeDetectionStrategy.OnPush) là cách hãm bớt: component chỉ được kiểm tra lại khi input đổi tham chiếu, khi có sự kiện phát ra từ chính nó, hoặc khi một signal nó đang đọc thay đổi. Repo dùng OnPush ở 427 chỗ — nghĩa là gần như mọi component.

Điểm cộng khi phỏng vấn

Nói thêm về zoneless (chế độ không Zone.js, ổn định từ Angular 20): khi bỏ Zone.js, CD được kích hoạt bởi chính signal thay vì bởi "vá" API trình duyệt. Các lifecycle hook không đổi tên, không đổi thứ tự — chỉ có tần suất các hook *Checked giảm mạnh. Repo này chưa bật zoneless, và có thể nói thẳng: đó là bước nâng cấp tiếp theo hợp lý sau khi đã phủ OnPush + signal.

06

Thời signal: những hook "kiểu mới"

Từ Angular 16 đến 21, ba nhóm API mới đã thay thế phần lớn công dụng của lifecycle hook cổ điển. Repo này là ví dụ sống: 526 chỗ dùng computed() nhưng chỉ 3 chỗ dùng ngOnChanges.

1 · DestroyRef.onDestroy() — thay ngOnDestroy

DestroyRef là một service Angular tiêm vào cho bạn, cho phép đăng ký hàm dọn dẹp mà không cần class phải implements OnDestroy. Nhờ vậy code dọn dẹp nằm ngay cạnh code khởi tạo, và dùng được cả trong hàm tiện ích (không phải class).

// projects/ui/src/custom/deferered-section/deferered-section.component.ts:39
constructor() {
  afterNextRender({ read: () => this.handleImplementWhenDomStable() });
  this.destroyRef.onDestroy(() => this.handleComponentDestroy());
}
Khởi tạo và dọn dẹp đứng cạnh nhau — đọc một chỗ là thấy đủ cặp.

2 · afterNextRender() / afterEveryRender() — lấy phần lớn việc của ngAfterViewInit

Render ở tên hàm này là Angular dựng xong DOM, chưa phải trình duyệt vẽ lên màn hình — hai việc khác nhau và của hai chủ thể khác nhau. afterNextRender chạy một lần, sau khi cả cây component đã dựng xong DOM và trước lúc trình duyệt vẽ (nhờ vậy sửa thẻ ở đây thì người dùng không thấy màn hình nháy); afterEveryRender (tên cũ là afterRender, đổi tên từ Angular 20) chạy sau mọi lần vẽ. Hai điểm hơn hẳn ngAfterViewInit:

  • Chỉ chạy trên trình duyệt — tự động bỏ qua khi SSR, không cần tự viết if (isPlatformBrowser(...)).
  • Có các "phase" (giai đoạn) earlyRead / write / read, giúp gom việc đọc và ghi DOM lại, tránh layout thrashing (đọc–ghi DOM xen kẽ khiến trình duyệt phải tính lại bố cục liên tục).
// projects/ui/src/utils/dropdown-helpers.ts:19
afterNextRender({
  read: () => {
    if (isDestroyed) {
      // Prevent early destroyed component causing memory leak in afterNextRender
      return;
    }
    const elementRef = elementRefFn();
    width.set(Math.round(elementRef.nativeElement.clientWidth));
    resizeObserver = new ResizeObserver(...);
  },
});
Chi tiết đáng kể ra khi phỏng vấn

Đoạn trên là bài học thật từ repo: component có thể bị huỷ trước khi lần render kế tiếp xảy ra. Vì vậy cờ isDestroyed được bật trong destroyRef.onDestroy() và kiểm tra lại ở đầu callback. Đây đúng là loại chi tiết mà người phỏng vấn muốn nghe: bạn đã gặp bug thật, không chỉ đọc tài liệu.

2b · Vậy ngAfterViewInit còn để làm gì?

Chữ "thay" ở trên dễ gây hiểu nhầm là hook cũ đã chết. Angular 21 không đánh dấu ngAfterViewInit là deprecated (không khuyến khích dùng, sẽ bị gỡ ở bản sau), và nó vẫn giữ ba việc mà afterNextRender không làm được:

  1. Chạy cả trên máy chủ. afterNextRender bị Angular bỏ qua hoàn toàn khi dựng SSR. Việc nào cần view đã dựng nhưng không đụng số đo, và kết quả của nó phải có mặt trong HTML máy chủ trả về, thì chỉ ngAfterViewInit làm được.
  2. Gọi được ở mọi chỗ trong class. ngAfterViewInit là một phương thức bình thường. afterNextRender đòi injection context (ngữ cảnh tiêm — khoảnh khắc Angular đang dựng đối tượng và biết nó thuộc về ai, tức trong constructor hoặc lúc gán giá trị đầu cho thuộc tính); ra khỏi đó là lỗi NG0203, phải tự cầm Injector truyền vào.
  3. Chạy sớm hơn. afterNextRender đợi cả cây component dựng xong. Việc chỉ cần view của chính mình thì đợi cả cây là trễ vô ích.
// Nối nhãn với ô nhập cho trình đọc màn hình.
// Vì sao KHÔNG dùng afterNextRender: thuộc tính này phải nằm sẵn trong
// HTML máy chủ trả về — trình đọc màn hình và bộ máy tìm kiếm đọc bản đó.
// Vì sao ngAfterViewInit là đủ: chỉ GHI thuộc tính, không đọc số đo nào,
// nên không cần đợi trình duyệt tính bố cục.
export class ONhapCoNhan implements AfterViewInit {
  private readonly nhan = viewChild.required<ElementRef<HTMLElement>>('nhan');
  private readonly o    = viewChild.required<ElementRef<HTMLInputElement>>('o');

  ngAfterViewInit() {
    this.o().nativeElement.setAttribute('aria-labelledby', this.nhan().nativeElement.id);
  }
}
Ghi thuộc tính tĩnh, không đổi state Angular ⇒ không có nguy cơ ExpressionChangedAfterItHasBeenChecked.
Quy tắc chọn: việc có đụng số đo thật hoặc window/document không? Có ⇒ afterNextRender. Không, mà cần theo dõi một truy vấn view xuất hiện/biến mất ⇒ effect(). Không, chạy một lần, và cần cả trên máy chủ ⇒ ngAfterViewInit.
Chỗ bị cắt nhiều nhất

Việc phổ biến nhất mà ngAfterViewInit từng gánh là "đợi tới đây thì @ViewChild mới có giá trị". Việc đó nay thuộc về viewChild() đọc trong effect() — vừa chạy khi thẻ có, vừa chạy lại nếu khối @if tắt rồi bật, thứ mà một hook chạy đúng một lần không làm được. Cộng lại: afterNextRender lấy phần "đụng DOM thật", effect() lấy phần "đợi truy vấn có giá trị", phần còn lại cho ngAfterViewInit là khúc giữa — không nhiều, nhưng có thật.

3 · input() + computed() + effect() — thay ngOnChanges/ngDoCheck

Signal (tín hiệu) là ô chứa giá trị biết ai đang đọc mình; khi giá trị đổi, nó tự báo cho những chỗ phụ thuộc. computed() là signal dẫn xuất (tự tính lại từ signal khác). effect() là "hiệu ứng phụ": chạy lại mỗi khi signal nó đọc thay đổi.

// Cách cũ                              // Cách mới (repo đang dùng)
ngOnChanges(c: SimpleChanges) {        fullName = computed(() =>
  if (c['first'] || c['last'])            this.first() + ' ' + this.last()
    this.fullName = ...;               );
}
Ranh giới cần nhớ

computed() dùng khi bạn cần giá trị dẫn xuất — luôn ưu tiên. effect() chỉ dùng khi cần tác động ra bên ngoài: ghi localStorage, gọi thư viện thứ ba, đồng bộ với DOM. Đặt effect() mà chỉ để gán vào một field khác là dấu hiệu bạn nên dùng computed(). Muốn đọc một signal trong effect mà không đăng ký phụ thuộc vào nó thì bọc bằng untracked() — repo dùng đúng kỹ thuật này ở dropdown-checkbox.component.ts:320.

07

Bộ câu hỏi phỏng vấn + đáp án

Kể đủ 8 lifecycle hook theo thứ tự.

ngOnChanges → ngOnInit → ngDoCheck → ngAfterContentInit → ngAfterContentChecked → ngAfterViewInit → ngAfterViewChecked → ngOnDestroy. constructor chạy trước tất cả nhưng không phải hook của Angular.

Vì sao gọi HTTP nên đặt ở ngOnInit chứ không phải constructor?

Vì input chỉ được gán sau khi constructor kết thúc — trong constructor bạn sẽ gọi API với tham số undefined. Ngoài ra tách side effect (tác dụng phụ) ra khỏi constructor giúp unit test dễ hơn: test có thể tạo instance mà không kích hoạt gọi mạng.

ngOnChanges không nổ dù dữ liệu rõ ràng đã đổi — vì sao?

Bạn sửa nội dung bên trong object/mảng cũ. Angular chỉ so sánh tham chiếu. Sửa this.items.push(x) ⇒ vẫn cùng địa chỉ ⇒ không nổ. Phải this.items = [...this.items, x]. (Nếu dùng signal thì update() với giá trị mới cũng phải theo nguyên tắc bất biến tương tự.)

Lỗi ExpressionChangedAfterItHasBeenCheckedError là gì, sửa thế nào?

Ở chế độ dev, Angular chạy kiểm tra hai lần mỗi nhịp để bắt lỗi. Nếu ở lần hai giá trị đã khác lần một — thường do bạn đổi state trong ngAfterViewInit hoặc ngAfterViewChecked — Angular báo lỗi này. Cách sửa theo thứ tự ưu tiên: (1) chuyển logic lên ngOnInit; (2) dùng computed() thay vì gán tay; (3) hoãn sang nhịp sau bằng setTimeout hoặc afterNextRender — chính là cách ubck-echarts-core.ts:200 đang làm.

Có phải mọi subscription đều phải unsubscribe trong ngOnDestroy?

Không. Luồng tự complete (HttpClient, toSignal, pipe async trong template) thì Angular/RxJS tự dọn. Chỉ luồng vô hạn mới cần: interval, fromEvent, Subject dùng chung. Cách gọn nhất hiện nay là toán tử takeUntilDestroyed() từ @angular/core/rxjs-interop, hoặc destroyRef.onDestroy() như repo đang dùng ở 65 chỗ.

Signal đã thay được toàn bộ lifecycle hook chưa?

Chưa và cũng không nên. Signal thay tốt cho ngOnChanges (bằng computed) và ngDoCheck (không cần nữa). afterNextRender thay tốt cho ngAfterViewInit, DestroyRef thay tốt cho ngOnDestroy. Nhưng ngOnInit vẫn hữu ích và vẫn được khuyến nghị cho khởi tạo phụ thuộc input — repo còn 140 chỗ dùng. Câu trả lời chuẩn là: "cùng tồn tại, chọn theo việc", không phải "cái mới xoá cái cũ".

Chuyển sang zoneless thì lifecycle có đổi không?

Tên và thứ tự hook không đổi. Cái đổi là khi nào nhịp CD chạy: thay vì Zone.js báo sau mỗi tác vụ bất đồng bộ, CD chỉ chạy khi có signal thay đổi hoặc có markForCheck(). Hệ quả thực tế: các hook *Checked chạy ít hơn nhiều — nên code nào lỡ dựa vào việc ngAfterViewChecked "chạy liên tục" sẽ hỏng khi bật zoneless.

Directive có lifecycle không?

Có. Directive (chỉ thị — class gắn hành vi vào một thẻ HTML sẵn có, không có template riêng) dùng chung hầu hết các hook, trừ nhóm liên quan tới view/content của chính nó. Bằng chứng trong repo: ubck-echarts-core.ts là một @Directive cài đủ OnChanges, OnInit, AfterViewInit, OnDestroy.
