Là gì

Một dấu bằng nhiều hơn, một bước ít đi

JavaScript có hai toán tử (operator — ký hiệu thực hiện một phép tính) so sánh bằng:

Lỏng

== — abstract equality

So sánh sau khi ép kiểu (type coercion — tự động đổi giá trị sang kiểu khác). Hai vế khác kiểu thì JavaScript tự nắn cho về cùng kiểu rồi mới so.

1 == '1'      // true — chuỗi '1' bị đổi thành số 1
0 == false    // true — false bị đổi thành số 0
Nghiêm

=== — strict equality

So sánh không ép kiểu. Khác kiểu là false ngay, khỏi bàn thêm. Đây là hành vi mà hầu hết ngôn ngữ khác gọi là "bằng nhau".

1 === '1'     // false — số khác chuỗi
0 === false   // false — số khác boolean

Với nguyên thuỷ (primitive — số, chuỗi, boolean, null, undefined, symbol, bigint) thì cả hai so giá trị. Với đối tượng (object — mảng, đối tượng, hàm) thì cả hai đều so địa chỉ ô nhớ, không so nội dung — nên {} === {} lẫn {} == {} đều là false.

Câu chốt cả bài: === trả lời "hai vế có giống hệt nhau không". == trả lời "sau khi tôi tự sửa hai vế cho khớp kiểu thì chúng có giống nhau không" — và cách nó tự sửa mới là thứ gây bất ngờ, chứ không phải phép so sánh.

Cơ chế

== quyết định theo sáu bước

Khi gặp a == b, JavaScript chạy một thuật toán (algorithm — dãy bước cố định) đi từ trên xuống, gặp bước nào khớp thì dừng ở đó:

Đọc ngược sơ đồ sẽ thấy vì sao [] == false lại là true: bước 4 đổi false thành 0, bước 5 đổi [] thành chuỗi rỗng '', bước 3 đổi '' thành 0, và cuối cùng bước 1 so 0 với 0. Bốn lần biến hình chỉ để nói "mảng rỗng bằng false".

Bảng tra

Những cặp hay làm người ta ngã ngửa

Cạm bẫy lớn nhất — == không bắc cầu: 0 == '' đúng, 0 == '0' đúng, nhưng '' == '0' lại sai. Trong toán học, quan hệ "bằng" mà không bắc cầu là quan hệ hỏng. Vì thế không có cách nào "học thuộc cho quen" == — mọi trực giác đều sẽ trượt ở đâu đó.

Ngoại lệ

=== vẫn sai ở hai chỗ: NaN và -0

So nghiêm không phải là thần thánh. Nó thừa hưởng đúng hai điểm kỳ quặc của chuẩn số:

NaN === NaN        // false — dù rõ ràng là "cùng một thứ"
0 === -0           // true — dù đây là hai giá trị khác nhau về dấu

// Muốn "giống hệt" đúng nghĩa thì dùng Object.is:
Object.is(NaN, NaN)   // true
Object.is(0, -0)     // false

// Kiểm tra NaN một cách tường minh:
Number.isNaN(x)       // đúng: chỉ true khi x thật sự là NaN
isNaN(x)              // sai: hàm cũ, ép kiểu trước — isNaN('abc') là true

Object.is (so sánh "giống hệt" theo chuẩn SameValue) giống === ở mọi trường hợp còn lại, nên chỉ lôi ra khi thực sự cần phân biệt NaN hoặc dấu của số không — dùng nó thay === ở khắp nơi là làm mã khó đọc mà chẳng được gì.

Được gì — mất gì

Ưu điểm và nhược điểm của ==

+Mặt lợi

  • Gộp null và undefined trong một phép so — đây là công dụng hợp lệ duy nhất và cũng là lý do duy nhất để giữ == trong mã hiện đại.
  • Viết ngắn khi dữ liệu vào không rõ kiểu, ví dụ tham số lấy từ đường dẫn luôn là chuỗi trong khi mã lại giữ số.
  • Được các bộ kiểm mã cho phép có chọn lọc: quy tắc eqeqeq của ESLint (bộ kiểm mã — công cụ soi lỗi và soi phong cách viết) có tuỳ chọn 'always', { null: 'ignore' }, cho đúng một ngoại lệ này.

Ví dụ mặt lợi

if (x == null) { … }
// Bắt cả null lẫn undefined, không bắt 0, '' hay false.
// Bản viết bằng === phải dài gấp đôi:
if (x === null || x === undefined) { … }

// Bản hiện đại, rõ ràng hơn cả hai:
if (x ?? false) { … }        // toán tử hợp nhất null
const ten = x?.ten ?? 'Không rõ';

−Mặt hại

  • Không bắc cầu — quan hệ bằng mà a == b, a == c nhưng b != c thì không thể suy luận được bằng trực giác.
  • Giấu lỗi kiểu dữ liệu. Chuỗi lọt vào chỗ đáng lẽ là số vẫn chạy êm, tới khi làm phép cộng mới vỡ ở một chỗ hoàn toàn khác.
  • Kết quả phụ thuộc valueOf/toString của đối tượng — bước 5 gọi vào chính mã của bạn, nên hai đối tượng "tưởng như" so được lại ra kết quả bất ngờ.
  • Chậm hơn một chút vì có thể phải chuyển kiểu vài vòng, tuy đây là lý do yếu nhất.
  • Người đọc sau phải dừng lại đoán: tác giả cố tình dùng ==, hay gõ thiếu một dấu bằng?

Ví dụ mặt hại

// ✗ id từ đường dẫn là chuỗi, id trong danh sách là số
const found = ds.find((r) => r.id == idTrenUrl);
// Chạy đúng… cho tới khi có bản ghi id = 0 và idTrenUrl = ''
// → khớp nhầm, mở sai bản ghi.

// ✗ soLuong lấy từ ô nhập là chuỗi rỗng khi người dùng xoá trắng
if (soLuong == 0) canhBao();
// '' == 0 là true → cảnh báo "số lượng bằng 0" khi ô đang trống

// ✗ đối tượng tự định nghĩa valueOf
const vi = { valueOf: () => 0 };
vi == false          // true (!)
vi === false         // false

Cách sống chung an toàn: dùng === và !== ở mọi nơi, bật quy tắc eqeqeq trong ESLint để máy nhắc thay người. Ngoại lệ duy nhất được phép là x == null khi muốn bắt cả null lẫn undefined — và nếu dự án đã dùng cú pháp mới thì ?. (optional chaining — truy cập an toàn) cùng ?? (nullish coalescing — hợp nhất null) còn nói rõ ý hơn. Khi hai vế có thể khác kiểu, hãy ép kiểu tường minh trước (Number(x) === y) thay vì để == ép ngầm.
