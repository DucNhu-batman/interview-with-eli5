Là gì

Xưởng ép nước mía và đóng chai công nghiệp

Trình duyệt web (như Chrome, Firefox, Safari) là một khách hàng cực kỳ "khó tính": nó hoàn toàn không hiểu cú pháp TypeScript (.ts), không biết @Component, inject() hay signal() là gì, và cũng không thể tự chạy các thẻ template lồng logic như @if hay @for.

Toàn bộ mã nguồn bạn viết giống như những cây mía thô: dài, nhiều lá thừa, cồng kềnh. Quá trình build (đóng gói mã nguồn) chính là một dây chuyền công nghiệp hiện đại:

  1. Máy ép bóc vỏ (AOT Compiler — ngc): Chuyển hoá toàn bộ cú pháp TypeScript và template HTML thành các câu lệnh JavaScript thuần tuý siêu nhanh điều khiển trực tiếp DOM.
  2. Rung cây rụng cành lá khô (Tree-shaking): Soát lại toàn bộ ứng dụng và các thư viện phụ thuộc. Bất kỳ hàm, lớp, hay tính năng nào bạn import nhưng không dùng tới đều bị cắt bỏ thẳng tay.
  3. Đóng chai và hút chân không (Bundler & Minification): Gom hàng trăm file mã nguồn rời rạc lại thành một vài gói bundle, rút gọn tên biến (như đổi tongTienThanhToan thành a), xoá sạch chú thích và khoảng trắng thừa.
  4. Dán tem mã vạch chống ôi thiu (Content Hashing): Đặt tên file kèm mã băm ngẫu nhiên theo nội dung (như main-7A2B9C.js) để trình duyệt lưu vào bộ nhớ đệm (cache) vĩnh viễn nhưng lập tức tải file mới mỗi khi bạn deploy bản cập nhật.

Bản chất cốt lõi: Lệnh ng build lấy vào hàng ngàn file .ts, .html, .scss lộn xộn của dự án và xuất xưởng ra một thư mục tĩnh dist/ chứa duy nhất: 1 file HTML vỏ rỗng (index.html), 1 file chứa linh hồn ứng dụng (main.js), 1 file hỗ trợ môi trường (polyfills.js), 1 file kiểu dáng (styles.css) cùng các mảnh tải lười (lazy chunks).

Cơ chế

Dây chuyền 4 bước: Từ phím gõ đến thư mục dist/

Dưới đây là sơ đồ chi tiết dòng chảy của mã nguồn từ lúc bạn gõ lệnh ng build cho tới khi các file thành phẩm được ghi ra ổ cứng.

Giải phẫu tệp

Bên trong thư mục dist/ có những gì?

Khi bạn chạy lệnh ng build xong, hãy mở thư mục dist/tên-app/browser/. Bạn sẽ thấy 5 nhân vật chính sau đây:

Trọng yếu

1. main-[hash].js

Trái tim của ứng dụng: Chứa toàn bộ mã nguồn bạn viết (Component, Service, Signal), cộng với phần khung chạy thời gian thực của Angular (Ivy runtime, Dependency Injection, Change Detection). Nó là file lớn nhất và bắt buộc phải tải xong thì app mới hiện chữ đầu tiên.

Môi trường

2. polyfills-[hash].js

Cầu nối tương thích trình duyệt: Chứa các đoạn mã vá lỗ hổng tính năng của trình duyệt. Trong ứng dụng dùng Zone.js, file này chứa chính mã nguồn của zone.js. Khi bạn bật chế độ Zoneless (Angular 18+), file này sẽ teo nhỏ đi đáng kể hoặc có thể bỏ hẳn.

Giao diện

3. styles-[hash].css

Bộ áo kiểu dáng: Toàn bộ mã CSS/SCSS toàn cục (khai báo trong styles.scss) được gộp lại thành một file duy nhất, đã loại bỏ khoảng trắng và xuống dòng để đạt kích thước nhỏ nhất.

Tải theo nhu cầu

4. chunk-[hash].js

Các mảnh xếp hình lười: Sinh ra khi bạn dùng loadComponent, loadChildren trong Router hoặc khối @defer. Trình duyệt không tải các file này lúc mở đầu, mà chỉ gửi request kéo về khi người dùng chuyển sang trang đó hoặc cuộn chuột tới nơi.

Soi lỗi

5. *.js.map (Source Map)

Bản đồ toạ độ gỡ lỗi: File này ánh xạ từng ký tự đã bị băm nát trong main.js quay ngược trở lại dòng code .ts ban đầu. Khi bật F12 ở môi trường phát triển (dev), trình duyệt đọc file map này để bạn có thể đặt điểm dừng (breakpoint) trên file TypeScript thật sự.

Cửa ngõ

6. index.html

Khung xương đón khách: Một file HTML tĩnh đơn sơ chứa thẻ <app-root></app-root>. Trong quá trình build, Angular CLI tự động chèn các thẻ <script src="main.js" type="module"> vào cuối thẻ <body>.

Tại sao có mã băm

Ý nghĩa của đoạn mã băm [hash] trên tên file

Tại sao tên file khi build ra luôn có dạng kỳ lạ như main-8F3A1D.js thay vì main.js? Đây là kỹ thuật Cache Busting:

  • Trình duyệt người dùng rất lười: khi tải một file JS về, nó sẽ lưu vào bộ nhớ đệm (cache) trên máy khách để lần sau mở lại không tốn 3G/Wifi tải lại.
  • Nếu máy chủ đặt tên cố định là main.js, khi bạn sửa code và deploy bản mới, khách hàng bấm F5 vẫn mở ra bản cũ rích trong máy họ!
  • Nhờ mã băm nội dung (Content Hash): Mã băm được tính toán dựa trên chính từng ký tự trong file. Code không đổi → mã băm giữ nguyên (khách dùng cache cũ siêu tốc); Code đổi 1 dấu chấm → mã băm đổi khác hoàn toàn (khách bắt buộc tải file mới). Bạn có thể tự tin cấu hình máy chủ Nginx/CDN cho phép lưu cache vĩnh viễn (Cache-Control: max-age=31536000, immutable).

Được gì — mất gì

Ưu điểm và nhược điểm của quy trình build hiện đại

+Mặt lợi

  • Bắt lỗi kiểu dữ liệu ở template: AOT compiler soi ra lỗi gọi sai tên biến hoặc sai kiểu ngay trong terminal, không để lỗi lọt ra môi trường thật.
  • Dung lượng nhỏ hơn tới 80%: Tree-shaking kết hợp Minification cắt bỏ toàn bộ code rác, chỉ đóng gói những gì thật sự chạy.
  • Tốc độ mở trang cực nhanh: Trình duyệt không tốn CPU biên dịch template lúc mở máy khách, tải JS về là render DOM được ngay.
  • Miễn nhiễm lỗi đè cache: Mã băm [hash] giúp máy chủ tận dụng bộ nhớ đệm tối đa mà người dùng không bao giờ bị kẹt ở phiên bản cũ.
  • esbuild siêu tốc (Angular 17+): Tốc độ build nhanh gấp 4 lần thế hệ Webpack cũ nhờ viết bằng ngôn ngữ Go và tận dụng đa nhân CPU.

Ví dụ mã Ivy sinh ra sau AOT

// Template bạn viết: <h1>Xin chào {{ ten() }}</h1>
// Sau khi AOT compile, biến thành các chỉ thị DOM thuần:
ɵɵelementStart(0, 'h1');
ɵɵtext(1);
ɵɵelementEnd();
// Khi cập nhật dữ liệu:
ɵɵtextInterpolate1('Xin chào ', ctx.ten(), '');

−Mặt hại

  • Nguy cơ lỗi tải mảnh (ChunkLoadError): Khi bạn deploy bản mới, các file chunk cũ bị xoá khỏi CDN, người dùng đang mở app bấm route mới sẽ bị lỗi 404.
  • Rủi ro lộ bí mật mã nguồn: Nếu vô tình bật Source Map (*.js.map) ở môi trường production, bất kỳ ai mở F12 cũng đọc được 100% code TypeScript gốc của bạn.
  • Tác dụng phụ cản trở Tree-shaking: Nếu thư viện hoặc code của bạn có chứa side-effects, bundler không dám xoá và khiến main.js phình to.
  • Bộ nhớ RAM lúc build: Các dự án Enterprise khổng lồ hàng ngàn component đòi hỏi máy chủ CI/CD phải có dung lượng RAM lớn (thường cần --max_old_space_size=8192).

Ví dụ cạm bẫy lộ Source Map

// ✗ angular.json cấu hình lộ mã nguồn ra ngoài Internet:
"configurations": {
  "production": {
    "sourceMap": true  // ✗ Người dùng F12 thấy sạch logic nghiệp vụ bí mật!
  }
}
// Chữa: "sourceMap": { "scripts": false, "hidden": true }
// (chỉ sinh map đẩy lên Sentry theo dõi lỗi ngầm, không lộ ra public)

Cấu hình chuẩn mực của một Senior trong angular.json:

  • Chuyển sang Application Builder: Dùng builder mới @angular-devkit/build-angular:application để tận dụng tốc độ của esbuild thay cho Webpack đời cũ.
  • Kiểm soát ngân sách kích thước (Budgets): Đặt ngưỡng cảnh báo nếu main.js vượt quá 500KB và báo lỗi (error) nếu vượt quá 1MB để ngăn ngừa đồng nghiệp vô tình kéo thư viện nặng vào dự án.
  • Bảo vệ Source Map: Tuyệt đối tắt sourceMap: false cho public web, hoặc dùng hidden: true nếu cần tích hợp hệ thống bắt lỗi tự động.
// angular.json — Cấu hình xuất xưởng chuẩn cho Production
"architect": {
  "build": {
    "builder": "@angular-devkit/build-angular:application",
    "options": {
      "outputPath": "dist/my-app",
      "browser": "src/main.ts"
    },
    "configurations": {
      "production": {
        "optimization": true,
        "sourceMap": false,
        "budgets": [
          { "type": "initial", "maximumWarning": "500kB", "maximumError": "1MB" }
        ]
      }
    }
  }
}

Nói trong phỏng vấn

Góc nhìn Senior: Tường tận từng byte trong bundle

Trả lời 30 giây: "Quy trình build của Angular là chuỗi pipeline gồm hai giai đoạn chính: biên dịch và đóng gói. Đầu tiên, trình biên dịch AOT (ngc) phân tích cú pháp TypeScript và biên dịch toàn bộ template HTML thành các hàm chỉ thị Ivy bytecode thuần túy, đồng thời kiểm tra kiểu dữ liệu nghiêm ngặt. Tiếp theo, bộ đóng gói hiện đại (esbuild trong Application Builder) quét cây phụ thuộc, thực hiện Tree-shaking để vứt bỏ các đoạn mã thừa, băm nhỏ các route và khối @defer thành các lazy chunk độc lập, rút gọn tên biến (minification) và gắn mã băm nội dung (content hash) vào tên file để tối ưu bộ nhớ đệm HTTP. Kết quả cuối cùng trong thư mục dist/ là index.html, main.js, polyfills.js và các file chunk đã sẵn sàng để phục vụ trên CDN."

Câu hỏi kinh điển

Biên dịch AOT (Ahead-of-Time) khác gì với JIT (Just-in-Time) và tại sao Angular bỏ JIT ở production?

Kiểm tra xem ứng viên có hiểu tại sao Angular đời cũ bị chê nặng nề còn Angular hiện đại lại nhẹ và nhanh.

Cách trả lời ăn điểm: Với JIT, mã TypeScript/HTML được tải nguyên vẹn về máy người dùng, và trình duyệt phải tự nạp cả bộ máy biên dịch Angular Compiler (nặng khoảng 1–2MB) để dịch template ngay trên máy khách lúc vừa mở web, khiến FCP cực kỳ chậm. Với AOT, toàn bộ việc dịch template sang lệnh JavaScript được thực hiện sẵn ngay trên máy của lập trình viên hoặc máy chủ CI/CD trước khi xuất xưởng. Nhờ đó, file tải về trình duyệt chỉ còn là mã JS thuần, không phải kèm compiler, kích thước bundle giảm một nửa và ứng dụng khởi chạy tức thì.

Cạm bẫy hiệu năng

Tree-shaking hoạt động ra sao và làm sao để đảm bảo code của bạn không bị "miễn nhiễm" với Tree-shaking?

Đánh giá kiến thức chuyên sâu về cơ chế hoạt động của trình đóng gói mã nguồn (Bundler).

Cách trả lời ăn điểm: Tree-shaking dựa trên cú pháp tĩnh của chuẩn ES Modules (import và export). Bundler sẽ bắt đầu từ điểm vào (entry point) main.ts và duyệt theo đồ thị phụ thuộc; hàm nào không có cạnh nối tới sẽ bị loại bỏ. Tuy nhiên, nếu một file có chứa mã "tác dụng phụ" (side-effects — ví dụ: gán biến toàn cục window.myVar = 1, hay chạy lệnh ngay khi nạp file), bundler sẽ không dám xoá vì sợ làm vỡ logic ngầm. Để tối ưu: luôn viết các hàm thuần (pure functions), cấu hình "sideEffects": false trong package.json cho các thư viện nội bộ, và ưu tiên dùng providedIn: 'root' thay vì khai báo service trong module.

Bảo mật & Vận hành

Có nên đẩy file Source Map (.js.map) lên môi trường Production không?

Một câu hỏi đo lường tư duy bảo mật và kiến thức vận hành hệ thống thực tế.

Cách trả lời ăn điểm: Tuyệt đối không đẩy công khai file .js.map lên máy chủ web production cho người dùng cuối. Nếu có file map, bất kỳ ai mở DevTools cũng có thể đọc và tải toàn bộ mã nguồn TypeScript gốc, bao gồm cấu trúc thư mục, các quy tắc nghiệp vụ nội bộ và các endpoint bảo mật. Giải pháp chuẩn là tắt sourceMap: false cho web public, hoặc dùng chế độ hidden: tạo file source map nhưng không kèm link trỏ trong file JS, sau đó tải riêng các file map này lên hệ thống giám sát lỗi tập trung (như Sentry, Datadog) để giải mã dấu vết ngăn xếp lỗi (stack trace) khi có sự cố xảy ra.

Kiến trúc v17+

Sự khác biệt giữa Webpack Builder truyền thống và Application Builder (esbuild) là gì?

Kiểm tra khả năng cập nhật các công nghệ tiên tiến nhất của hệ sinh thái Angular.

Cách trả lời ăn điểm: Webpack builder cũ (@angular-devkit/build-angular:browser) chạy trên môi trường Node.js viết bằng JavaScript nên tốc độ xử lý tuần tự và khá chậm đối với dự án lớn. Từ Angular 17, Google giới thiệu @angular-devkit/build-angular:application sử dụng esbuild (viết bằng ngôn ngữ Go) kết hợp với Vite cho dev server. esbuild tận dụng tối đa kiến trúc đa nhân (multi-threading) của CPU hiện đại, giúp thời gian build production nhanh hơn 3–5 lần, thời gian khởi động dev server giảm từ hàng chục giây xuống gần như tức thì (dưới 2 giây), và hỗ trợ sẵn chuẩn nạp ESM hiện đại.

Quan niệm non tay cần tránh: "Mã nguồn TypeScript chạy trực tiếp trên trình duyệt giống như JavaScript." — Trình duyệt không bao giờ chạy được TypeScript hay template Angular. Hiểu rõ từng giai đoạn của pipeline build giúp bạn biết cách kiểm soát dung lượng file, không bao giờ để lọt lỗi bảo mật Source Map và biết chính xác tại sao file main.js của mình lại phình to.
