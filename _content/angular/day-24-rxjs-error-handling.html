Là gì

Lỗi là dấu chấm hết, trừ khi bạn chặn nó

RxJS (thư viện lập trình phản ứng — xử lý dữ liệu đến dần theo thời gian) coi mọi thứ là observable (luồng dữ liệu — thứ lần lượt phát ra từng giá trị, thay vì trả về một lần như hàm thường). Khi một luồng ném lỗi, nó chấm dứt vĩnh viễn: không phát thêm giá trị nào nữa, kể cả khi nguồn còn dữ liệu.

Với một luồng gắn vào ô tìm kiếm, điều đó nghĩa là sau một lần API (giao diện lập trình — điểm gọi tới máy chủ) lỗi, gõ tiếp cũng không còn gì xảy ra — một trong những bug (lỗi phần mềm) khó chịu nhất của người mới học RxJS.

this.api.tim(tuKhoa).pipe(                        // pipe = ống nối các toán tử
  retry({ count: 2, delay: 1000 }),               // thử lại 2 lần, cách nhau 1 giây
  catchError((loi) => {
    this.toast.error(getApiErrorMessage(loi));    // toast = thông báo nổi ở góc màn
    return of([]);                               // trả luồng dự phòng → luồng SỐNG TIẾP
  }),
  finalize(() => this.dangTai.set(false)),        // chạy dù thành công hay lỗi
).subscribe((ds) => this.ketQua.set(ds));         // subscribe = đăng ký nhận giá trị

Cả bài gói trong một câu: catchError không “sửa” lỗi, nó thay luồng đã chết bằng một luồng khác còn sống. Vì thế câu hỏi quan trọng nhất luôn là: bạn đặt nó ở đâu — luồng nào bị thay thế.

Cơ chế

Nhìn bằng hình: luồng chết và luồng được cứu

Người dùng gõ a, rồi ab — request (lời gọi tới máy chủ) của ab lỗi. Sau đó họ gõ tiếp abc, abcd. Hai hàng dưới đây là hai kết cục:

Vị trí của catchError quyết định phạm vi cứu. Đặt bên trong switchMap (toán tử đổi mỗi giá trị thành một luồng mới, huỷ luồng cũ) thì chỉ request đó chết, luồng ngoài vẫn sống. Đặt bên ngoài thì chính luồng ngoài bị thay thế — người dùng gõ tiếp sẽ không còn phản hồi, đúng như hàng trên của hình.

Ví dụ cụ thể

Bốn tình huống gặp hằng ngày trong dự án

1 · Ô tìm kiếm chết sau một lần mạng chập. Cùng một danh sách toán tử, chỉ khác chỗ đặt catchError, mà một bên hỏng hẳn màn hình:

Sai — cứu nhầm luồng

catchError nằm ngoài

Lỗi làm luồng ngoài (luồng từ khoá) bị thay bằng of([]). Luồng từ khoá coi như kết thúc: người dùng gõ tiếp, không ai lắng nghe nữa, phải tải lại trang mới dùng được.

tuKhoa$.pipe(
  debounceTime(300),                       // chờ 300ms ngừng gõ
  switchMap((tk) => this.api.tim(tk)),
  catchError(() => of([])),               // ✗ thay luôn luồng từ khoá
).subscribe((ds) => this.ketQua.set(ds));
Đúng — cứu đúng request

catchError nằm trong

Lỗi chỉ giết luồng con (một request), luồng từ khoá không hề biết có lỗi và vẫn nhận phím tiếp theo.

tuKhoa$.pipe(
  debounceTime(300),
  switchMap((tk) =>
    this.api.tim(tk).pipe(
      catchError((loi) => {              // ✓ trong switchMap
        this.loi.set(getApiErrorMessage(loi));
        return of([]);
      }),
    ),
  ),
).subscribe((ds) => this.ketQua.set(ds));

2 · Nút Lưu: lỗi trùng dữ liệu phải hiện dưới ô nhập, lỗi khác mới toast. Đây là quy ước bắt buộc của dự án — backend (máy chủ) trả HTTP 409 kèm errorCode: "CONFLICT" và câu chữ tiếng Việt, frontend (phía trình duyệt) in nguyên câu đó inline (ngay dưới ô nhập), không tự chế câu mới:

const QUY_TAC: ServerFieldErrorRule[] = [
  { control: 'code', match: /mã/i },   // câu lỗi có chữ "mã" → gắn vào ô Mã
  { control: 'name' },                // rule cuối không match = mặc định
];

this.api.taoMoi(form.getRawValue()).pipe(
  finalize(() => this.dangLuu.set(false)),          // nút Lưu luôn được mở lại
).subscribe({
  next: () => {
    this.unsavedChangesService.allowNextNavigation(); // khỏi hỏi "rời trang?" sau khi lưu
    this.navigateToList();
  },
  error: (loi) => {
    if (applyServerFieldError(form, loi, QUY_TAC)) return; // đã hiện inline → KHÔNG toast
    this.toast.show({
      severity: 'error',
      summary: getApiErrorMessage(loi) || 'Lưu không thành công',
      life: 5000,
    });
  },
});

Chú ý sự khác nhau: catchError trong pipe giữ luồng sống, còn nhánh error của subscribe là nơi nhận tin luồng đã chết. Với một lần bấm Lưu thì luồng chết là đúng — không có gì để chảy tiếp, nên dùng nhánh error là hợp lý. Nhưng nếu nút Lưu ấy nằm trong một luồng dài (ví dụ clickLuu$.pipe(exhaustMap(...))) thì phải đặt catchError bên trong exhaustMap, không thì lỗi lần đầu làm nút Lưu chết hẳn.

3 · Chỉ thử lại những lỗi đáng thử lại. retry mù quáng sẽ gọi lại cả lỗi 400 (dữ liệu sai) hay 403 (không có quyền) — vô ích và làm nặng máy chủ. Dùng delay dạng hàm để tự quyết định, kèm exponential backoff (giãn dần khoảng chờ):

retry({
  count: 3,
  delay: (loi, lanThu) => {                       // lanThu: 1, 2, 3…
    const ma = (loi as HttpErrorResponse).status;
    const dangThuLai = ma === 0 || ma === 408 || ma >= 500; // mất mạng / quá hạn / lỗi máy chủ
    if (!dangThuLai) return throwError(() => loi);  // 4xx → ném ngay, không thử lại
    return timer(lanThu * 1000);                    // chờ 1s, 2s, 3s rồi thử lại
  },
})

4 · Màn chi tiết tải song song ba API, một cái hỏng không được làm trắng cả trang. forkJoin (gộp nhiều luồng, chờ tất cả xong) có tính “được ăn cả ngã về không”: một nguồn lỗi là cả cụm lỗi. Vì vậy nguồn nào không sống còn thì bọc catchError riêng cho nó:

forkJoin({
  chiTiet: this.api.layChiTiet(id),                              // thiếu cái này thì màn vô nghĩa → để lỗi
  lichSu:  this.api.layLichSu(id).pipe(catchError(() => of([]))),   // hỏng thì tab Lịch sử rỗng
  dinhKem: this.api.layDinhKem(id).pipe(catchError(() => of([]))),  // hỏng thì không có tệp đính kèm
}).pipe(
  finalize(() => this.dangTai.set(false)),
).subscribe({
  next: (kq) => this.duLieu.set(kq),
  error: (loi) => this.loiTai.set(getApiErrorMessage(loi)),          // chỉ khi chiTiet hỏng
});

Bảng tra

Toán tử điều kiện — dùng cái nào, lúc nào

Toán tửLàm gì — ví dụ trong dự án
iif()Chọn một trong hai luồng lúc đăng ký. Form dùng chung cho Thêm mới và Chỉnh sửa: iif(() => !!id(), api.capNhat(id()!, dl), api.taoMoi(dl)).
defaultIfEmpty()Luồng kết thúc mà chưa phát gì thì cấp một giá trị dự phòng. Dropdown lọc rỗng: defaultIfEmpty([]) để bảng vẫn vẽ được thay vì treo mãi ở trạng thái đang tải.
throwIfEmpty()Ngược lại: luồng rỗng thì coi là lỗi. Resolver (bộ nạp dữ liệu trước khi vào route) không tìm thấy bản ghi: throwIfEmpty(() => new Error('Không tìm thấy')) rồi chuyển sang màn 404.
every()Trả về true/false xem MỌI giá trị có thoả điều kiện không. Kiểm tra tất cả dòng đã chọn đều đang ở trạng thái Nháp trước khi cho phép xoá hàng loạt.
find()Lấy giá trị ĐẦU TIÊN thoả điều kiện rồi kết thúc luôn. Chờ tới lúc quyền của người dùng được nạp xong: find((ds) => ds.length > 0).
timeout()Không phải toán tử điều kiện, nhưng hay đi cùng: quá N mili giây chưa có phản hồi thì ném lỗi để catchError phía sau xử lý, tránh spinner (vòng xoay chờ) quay vô tận.

Được gì — mất gì

Ưu điểm và nhược điểm

+Mặt lợi

  • Xử lý lỗi nằm ngay trong luồng, không phải rải try/catch (bắt lỗi kiểu đồng bộ) khắp nơi.
  • retry chữa được lỗi mạng chập chờn mà người dùng không hề biết.
  • finalize đảm bảo tắt spinner trong mọi kịch bản, kể cả khi luồng bị huỷ giữa chừng.
  • Trả luồng dự phòng cho phép hiển thị dữ liệu cũ/rỗng thay vì màn hình trắng.
  • Cứu được từng phần, như ví dụ 4: một API phụ hỏng không kéo sập cả màn chi tiết.

Ví dụ mặt lợi

api.tim(tk).pipe(
  retry({ count: 2, delay: 1000 }),
  catchError((e) => { toast.error(getApiErrorMessage(e)); return of([]); }),
  finalize(() => this.dangTai.set(false)),
)
// Mạng chớp tắt: tự thử lại, người dùng không hề biết.
// Lỗi thật: hiện thông báo, danh sách rỗng, spinner luôn được tắt.

−Mặt hại

  • Nuốt lỗi quá tay. catchError(() => EMPTY) (luồng rỗng kết thúc ngay) làm lỗi biến mất không dấu vết, rất khó điều tra.
  • retry mù quáng sẽ thử lại cả lỗi 400/403 — vô ích và làm nặng máy chủ.
  • Đặt sai chỗ là hỏng luồng chính, lỗi biểu hiện rất khó hiểu (ví dụ 1).
  • Trùng thông báo. Vừa toast trong catchError vừa để interceptor (bộ chặn HTTP dùng chung) toast là người dùng thấy hai lần.
  • Thử lại việc không nên thử lại. retry trên một request tạo mới có thể sinh ra hai bản ghi trùng.

Ví dụ mặt hại

tuKhoa$.pipe(switchMap((tk) => api.tim(tk))).subscribe(…);
// ✗ không có catchError: API lỗi một lần → luồng CHẾT hẳn.
// Từ đó gõ tiếp không còn gì xảy ra, phải F5 mới dùng lại được.

catchError(() => EMPTY)
// ✗ nuốt lỗi không dấu vết: người dùng bấm Lưu, không có gì xảy ra,
// console sạch bong, không ai điều tra nổi

Quy ước của dự án này: lỗi nghiệp vụ 409/CONFLICT phải hiện inline dưới ô nhập bằng đúng câu backend trả về, không toast; và endpoint (địa chỉ API) create/update phải tắt trình xử lý lỗi toàn cục (ignoreErrorHandler: true) để tránh toast lặp — bù lại, nhánh error của facade phải tự toast những lỗi không phải CONFLICT.
