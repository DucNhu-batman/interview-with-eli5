Là gì

Cổng vào của một component

Mỗi component con là một hộp kín. Muốn đưa dữ liệu vào, phải mở sẵn một cái cổng có tên — đó là input (đầu vào). Cha gán vào cổng đó bằng property binding.

// Con — cách mới, dựa trên signal (Angular 17.1+)
export class TheSanPham {
  sp = input.required<SanPham>();          // bắt buộc
  noiBat = input(false);                   // có giá trị mặc định
  giaHienThi = computed(() => format(this.sp().gia));
}

// Cha
<app-the-san-pham [sp]="item()" [noiBat]="true" />

Vì sao nên chuyển sang input(): nó là signal, nên dùng được trong computed()/effect(), không cần ngOnChanges, và TypeScript biết chắc input.required luôn có giá trị.

Quy ước

Ba nguyên tắc giữ cho luồng dữ liệu sạch

  1. Một chiều. Con không sửa dữ liệu cha truyền xuống. Muốn báo thay đổi thì phát sự kiện ra (bài Day 8).
  2. Dùng "props pattern" cho nhóm dữ liệu liên quan. Dự án này quy ước gom nhiều đầu vào cùng chủ đề thành một object [props] thay vì rải chục input rời.
  3. Đầu vào là object thì cẩn thận với OnPush. Sửa ruột object cũ sẽ không kích hoạt cập nhật; hãy truyền object mới.

Được gì — mất gì

Ưu điểm và nhược điểm

+Mặt lợi

  • Component tái sử dụng được. Cùng một thẻ, đổi dữ liệu là ra màn hình khác.
  • Luồng dữ liệu một chiều dễ suy luận. Nhìn cha là biết con nhận gì.
  • Hợp đồng rõ ràng. Danh sách input chính là API của component, được TypeScript kiểm tra.
  • Dễ kiểm thử. Truyền đầu vào, kiểm tra đầu ra, không cần dựng cả màn hình.

Ví dụ mặt lợi

// Cùng một component, ba màn hình khác nhau dùng lại
<app-the-san-pham [sp]="spNoiBat()" [noiBat]="true" />
<app-the-san-pham [sp]="spTimKiem()" />
<app-the-san-pham [sp]="spGoiY()" />

// Và test không cần dựng cả màn hình:
fixture.componentRef.setInput('sp', { ten: 'A', gia: 1000 });

−Mặt hại

  • Truyền xuyên nhiều tầng rất mệt (prop drilling) — sâu quá thì nên dùng service dùng chung.
  • Object literal trong template tạo tham chiếu mới mỗi lần vẽ, làm OnPush chạy oan.
  • Quá nhiều input là dấu hiệu component ôm đồm nhiều việc.
  • @Input kiểu cũ có thể undefined ở lần chạy đầu, dễ sinh lỗi nếu dùng ngay trong constructor.

Ví dụ mặt hại

<app-the-san-pham [props]="{ ten: ten(), gia: gia() }" />
// ✗ object literal → tham chiếu mới mỗi chu kỳ
// → component OnPush vẫn phải vẽ lại liên tục, mất sạch lợi ích tối ưu

this.sp().gia = 2000;      // ✗ sửa ruột object cha truyền xuống
// → cha không biết dữ liệu đã đổi; và luồng một chiều bị phá vỡ

Từ điển

Thuật ngữ đã dùng

Thuật ngữNghĩa tiếng Việt
inputĐầu vào — cổng nhận dữ liệu từ component cha.
signalÔ chứa giá trị có thể theo dõi; đọc bằng cách gọi như hàm.
computed()Signal dẫn xuất, tự tính lại khi nguồn đổi.
props patternGom nhiều đầu vào liên quan vào một object duy nhất.
prop drillingTruyền dữ liệu xuyên nhiều tầng component trung gian.
ngOnChangesHàm vòng đời chạy khi đầu vào thay đổi (cách cũ).
