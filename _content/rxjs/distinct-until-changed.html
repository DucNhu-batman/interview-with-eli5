Là gì

Chỉ so với người đứng ngay trước

distinctUntilChanged là toán tử (operator — hàm đặt trong pipe để nhào nặn luồng) giữ lại một giá trị duy nhất: giá trị vừa phát ra gần nhất. Giá trị mới đến mà bằng nó thì bị bỏ, khác nó thì được đi tiếp và trở thành mốc so sánh mới.

Điểm hay bị hiểu nhầm nhất nằm ở chữ UntilChanged: nó không nhớ toàn bộ lịch sử. Một giá trị đã từng xuất hiện vẫn được phát lại bình thường, miễn là ở giữa có giá trị khác chen vào.

Nhớ 1 giá trị

distinctUntilChanged()

So với giá trị liền trước. Bộ nhớ không đổi dù luồng chạy cả ngày.

a a b b b a c
→ a b a c
// chữ a thứ hai vẫn đi tiếp, vì trước nó là b
Nhớ tất cả

distinct()

So với mọi giá trị đã từng phát. Phải giữ một tập hợp lớn dần — luồng dài là phình bộ nhớ.

a a b b b a c
→ a b c
// chữ a thứ hai bị chặn vì đã từng xuất hiện

Câu chốt cả bài: distinctUntilChanged chống lặp liên tiếp, không chống trùng lặp. Nó rẻ và an toàn để đặt ở mọi nơi; distinct thì phải cân nhắc vì nó giữ lại mọi thứ đã đi qua.

Cơ chế

Nhìn bằng hình: khác nhau ở chỗ nhớ bao nhiêu

Vấn đề

Mặc định so bằng === — nên đối tượng luôn "khác nhau"

Hàm so sánh mặc định của RxJS chỉ đơn giản là (a, b) => a === b. Với nguyên thuỷ (primitive — số, chuỗi, boolean) thì đúng như mong đợi. Với đối tượng (object — mảng, đối tượng) thì === so địa chỉ ô nhớ chứ không so nội dung, nên hai đối tượng nội dung y hệt vẫn bị coi là khác nhau:

// Angular tạo một đối tượng MỚI mỗi lần form đổi giá trị
this.form.valueChanges.pipe(
  distinctUntilChanged(),   // ✗ không lọc được gì cả
).subscribe(luuNhap);
// { ten: 'An' } === { ten: 'An' } là false → mọi giá trị đều đi tiếp

Cách chữa là truyền vào hàm so sánh riêng (comparator — hàm nhận hai giá trị và trả về true nếu coi chúng là bằng nhau):

Cách viếtSo cái gìGhi chú
distinctUntilChanged()a === bChỉ đúng cho nguyên thuỷ. Với NaN cũng sai — NaN === NaN là false nên NaN lặp lại vẫn đi tiếp.
distinctUntilChanged((a, b) => a.id === b.id)Một trường khoáCách dùng phổ biến nhất cho danh sách bản ghi.
distinctUntilKeyChanged('id')Một trường khoáBản viết gọn của dòng trên, cùng ý nghĩa.
distinctUntilChanged(isEqual)Toàn bộ nội dung, đệ quyDùng hàm so sâu (deep equal) của thư viện tiện ích. Đúng nhưng tốn, đừng đặt trên luồng phát dày.
distinctUntilChanged((a, b) => JSON.stringify(a) === JSON.stringify(b))Chuỗi hoá rồi soViết nhanh nhưng phụ thuộc thứ tự khoá và không xử lý được undefined, Date, vòng lặp tham chiếu.

Bẫy ngược lại: viết comparator so sâu rồi đặt lên luồng phát hàng nghìn giá trị mỗi giây. Toán tử đáng lẽ để tiết kiệm lại trở thành chỗ tốn nhất trong pipe. Nếu chỉ cần biết "bản ghi có đổi không", hãy so đúng một trường khoá.

Trong Angular

Ba chỗ gần như luôn cần nó

// 1. Ô tìm kiếm — không gọi lại API khi giá trị thật ra không đổi
this.form.controls.tuKhoa.valueChanges.pipe(
  debounceTime(300),
  distinctUntilChanged(),        // gõ thừa rồi xoá về như cũ → không gọi lại
  switchMap((tk) => this.api.tim(tk)),
).subscribe((kq) => this.ketQua.set(kq));

// 2. Tham số trên đường dẫn — chỉ tải lại khi id thật sự đổi
this.route.paramMap.pipe(
  map((p) => p.get('id')!),
  distinctUntilChanged(),        // đổi tham số lọc mà id giữ nguyên → không tải lại
  switchMap((id) => this.api.chiTiet(id)),
).subscribe((ct) => this.chiTiet.set(ct));

// 3. Giá trị form dạng đối tượng — BẮT BUỘC có comparator
this.form.valueChanges.pipe(
  debounceTime(500),
  distinctUntilChanged((a, b) => a.ten === b.ten && a.tuoi === b.tuoi),
).subscribe(luuNhap);

Thứ tự trong pipe có ý nghĩa: đặt distinctUntilChanged sau debounceTime thì nó so hai giá trị đã lọc nhịp — đúng ý "so với lần gọi API trước". Đặt trước debounceTime thì nó so từng ký tự gõ vào, gần như không chặn được gì.

Được gì — mất gì

Ưu điểm và nhược điểm

+Mặt lợi

  • Cắt request thừa mà không cần biến nhớ giá trị cũ rải rác trong component.
  • Bộ nhớ cố định — luôn chỉ giữ đúng một giá trị, khác hẳn distinct.
  • Chặn vòng lặp cập nhật: luồng trạng thái phát lại cùng một giá trị sẽ không kích hoạt vẽ lại giao diện.
  • Ghép tự nhiên với debounceTime thành bộ đôi chuẩn của mọi ô tìm kiếm.
  • Comparator mở — muốn so theo tiêu chí nào cũng được, không bị bó vào ===.

Ví dụ mặt lợi

// Không có toán tử — phải tự giữ biến cũ:
let cu: string | null = null;
ô$.subscribe((v) => {
  if (v === cu) return;
  cu = v;
  tim(v);
});

// Có toán tử — một dòng, không biến trạng thái lạc lõng:
ô$.pipe(distinctUntilChanged()).subscribe(tim);

−Mặt hại

  • Vô dụng với đối tượng nếu quên comparator — và nó im lặng, không báo lỗi, chỉ là không lọc gì.
  • Không chặn được trùng lặp không liền kề — nhiều người tưởng nó làm việc của distinct.
  • Comparator so sâu rất tốn nếu đặt nhầm chỗ trên luồng phát dày.
  • Sai với NaN vì mặc định dùng ===; cần Object.is nếu luồng có thể chứa NaN.
  • Có thể nuốt mất tín hiệu "làm lại" — bấm nút Tải lại mà giá trị lọc không đổi thì không có gì đi tiếp.

Ví dụ mặt hại

// ✗ tưởng chặn được trùng, thật ra không
trangThai$.pipe(distinctUntilChanged())
// 'mở' 'đóng' 'mở' → cả ba đều đi tiếp

// ✗ nút Tải lại phát cùng một giá trị lọc → bị nuốt
boLoc$.pipe(
  distinctUntilChanged(),
  switchMap((f) => api.tim(f)),
)
// Bấm Tải lại mà không đổi bộ lọc → KHÔNG có request nào.
// Cần một luồng "làm mới" riêng, gộp bằng merge().

// ✗ NaN lặp lại vẫn lọt
of(NaN, NaN).pipe(distinctUntilChanged())
// phát ra 2 giá trị, không phải 1
of(NaN, NaN).pipe(distinctUntilChanged(Object.is))
// phát ra 1 giá trị — đúng

Cách sống chung an toàn: luồng phát nguyên thuỷ thì dùng thẳng distinctUntilChanged(). Luồng phát đối tượng thì luôn truyền comparator, và ưu tiên so một trường khoá (distinctUntilKeyChanged('id')) thay vì so sâu toàn bộ. Cần chặn trùng lặp trên cả lịch sử thì đó là việc của distinct — và khi dùng distinct, hãy nghĩ tới lúc luồng chạy suốt vài giờ.
